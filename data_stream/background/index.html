    Background 后台任务层 (src/backgrounds)¶

    文件路径：src/backgrounds/（含 27 个插件）

    管理所有长时间独立运行的后台守护任务——轮询硬件、订阅 Zenoh 消息、驱动状态机。在独立线程中持续运行，不阻塞主事件循环。

    与 Input 层（每个 tick 推送一次数据到 IOProvider）不同，Background 是"持续运行"的守护线程。二者的关系：Background 让 Provider 持续产出数据，Input 负责把数据翻译成标准格式写入 IOProvider。

    与 Simulators 的对比¶

    Background Simulator
    定位 真实硬件的后台守护 纯软件的仿真环境
    作用 驱动传感器、订阅消息、执行管线 模拟硬件反馈，用于无硬件调试
    在生产中使用 ✅ 核心组件 ❌ 仅开发/调试
    线程模型 线程池，每个 run() 在 while 中反复调用 线程池，每个 tick() 在 while 中反复调用

    基类设计¶

    class Background:
    def run(self) -> None:
        """子类重写：每轮执行的主逻辑（由编排器在 while 循环中反复调用）"""
        self.sleep(60)  # 默认睡 60 秒

    def sleep(self, duration: float) -> bool:
        """可中断的 sleep：收到 stop_event 时立即唤醒，不阻塞关闭流程"""
        ...

    def stop(self) -> None:
        """子类重写：清理资源（关闭连接、释放硬件、undeclare subscriber 等）"""
        ...

    编排器核心逻辑¶

    class BackgroundOrchestrator:
    def start(self):
        for background in self._config.backgrounds:
            background.set_stop_event(self._stop_event)
            # 每个 background 提交到独立线程
            self._background_executor.submit(self._run_background_loop, background)

    def _run_background_loop(self, background):
        while not self._stop_event.is_set():
            try:
                background.run()           # 反复调用
            except Exception:
                self._stop_event.wait(timeout=0.1)  # 出错后短暂等待再重试

    def stop(self):
        self._stop_event.set()             # 通知所有线程退出
        for bg in self._background_instances:
            bg.stop()                      # 调用各自的清理逻辑
        self._background_executor.shutdown(wait=True)

    按功能分类¶

    1. 硬件守护类 — Provider 启动器¶

    这类 Background 的 __init__ 只做一件事：创建对应的 Singleton Provider 并启动它。Provider 自身在后台运行（线程读传感器 / Zenoh 订阅），Background 本身通常不需要重写 run()。

    unitree_go2_locations.py UnitreeGo2LocationsProvider Go2 导航位置列表

    3. 抓取执行器 — 完整管线 ⭐¶

    这两个是整个系统中最复杂的 Background，不是简单的 Provider 启动器，而是完整的状态机驱动管线：

    文件 规模 核心能力
    arx_x5_grasp_executor.py ~500 行 Zenoh 订阅请求 → GraspSDK 姿态生成 → ARX X5 运动控制
    arx_x5_yolograsp_executor.py ~1200 行 YOLO 检测 → 选最优目标 → SAM 分割 → 抓取规划 → 执行

    完整抓取流程：

    arx_x5_yolograsp_executor (后台线程循环)
    │
    ├── Zenoh 订阅 "arx_x5/yolograsp/request"
    │     收到: {action: "grasp", target_name: "bottle", top_k: 50}
    │
    ├── D435Provider.get_realsense_snapshot()    # 拿最新 RGB-D 帧
    ├── YoloSDK.detect(rgb, "bottle")            # 检测目标物体
    ├── 选最高置信度 / 最中心的 Detection
    ├── SAM 分割 → 精确目标 Mask
    ├── GraspSDK.best_grasp(rgb, depth, ...)     # 生成最优抓取姿态
    ├── 坐标变换: 相机系 → 机械臂基座系
    │     (手眼标定矩阵 r_cam_to_end + t_cam_to_end)
    ├── GraspPlanner.plan()                      # 规划轨迹
    │     approach(接近) → grasp(夹取) → retreat(后退) → lift(抬起)
    ├── ARXX5MotionClient.send_joint_path()      # 发送关节角度序列
    │
    └── Zenoh 发布 "arx_x5/yolograsp/status"
           {status: "grasp_completed" | "grasp_failed" | "grasp_timeout"}

    关键配置参数：

    参数 说明
    grasp_url 外部抓取服务 URL（AnyGrasp / GraspNet）
    yolo_url 外部 YOLO 检测服务 URL
    r_cam_to_end / t_cam_to_end 手眼标定矩阵（相机→末端执行器）
    approach_distance 接近距离 (m)，默认 0.12
    grasp_retreat_distance 抓取后撤退距离 (m)，默认 0.01
    lift_distance 抬起高度 (m)，默认 0.15
    enable_motion false 时只发布姿态不驱动硬件（安全调试）

    4. 任务上下文状态机¶

    koala_fetch_mission_context.py — 将底层传感器状态翻译为"任务阶段"：

    监听源:
  ├── Zenoh: arx_x5/yolograsp/status     (抓取成功/失败/超时)
  ├── IOProvider: native_navigation_status (到达仓库/到达起点/导航中)
  └── UnitreeNativeSlamProvider: robot_pose (当前位置)

状态机输出 (通过 ContextProvider → Zenoh om/mode/context → 模式切换):
  ├── at_warehouse          → 触发: nav → grasp
  ├── grasp_completed       → 触发: grasp → nav (回家)
  ├── at_home               → 触发: nav → welcome
  ├── grasp_timeout         → 触发: grasp → nav (超时回家)
  ├── returning_home        → 记录归家途中
  └── ...

    它是 Input（传感器数据）和 Transition Rules（模式切换规则）之间的桥梁，让 LLM 只需要关注任务本身的决策，不需要解析底层传感器原始状态。

    架构设计要点¶

    1. 守护线程模型 — 每个 Background 在独立线程中运行，不阻塞 asyncio 主事件循环
    2. 可中断 sleep — sleep() 等待 stop_event，确保关闭时快速响应，避免僵尸线程
    3. Provider 作为生命周期管理者 — Background 只负责启动/停止 Provider，Provider 管理自己的采集线程
    4. 执行器模式 — 复杂管线（如抓取）不走主循环，而是在 Background 中独立运行，通过 Zenoh 与主循环解耦
    5. 状态机分层 — KoalaFetchMissionContext 将底层事件合成为高层任务阶段，避免 LLM 直接处理传感器原始数据
    6. 错误隔离 — 一个 Background 崩溃不会影响其他 Background 或主循环（try/except + 短暂等待后重试）
