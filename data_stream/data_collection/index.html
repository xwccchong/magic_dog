    MAGIC Input 和 Background 的数据获取机制详解¶

    整个数据流的核心设计模式是：Provider 单例 + 独立采集线程 + Input 轮询消费。

    两类数据获取方式¶

    方式 代表 启动方式 数据流
    Input 自驱动 UnitreeGo2Odom Input 构造时自己创建 Provider Provider 内部线程 → self.position → _poll()
    Background 驱动 D435 (相机) BackgroundOrchestrator 线程池提交 独立子进程采集 → Provider 内存 → Input 的 VLM 线程

    一、UnitreeGo2Odom — Input 自驱动模式¶

    这是最简单的模式，没有对应的 Background。

    调用链路¶

    配置: agent_inputs: [{type: "UnitreeGo2Odom"}]
         │
         ▼
① config.py: _load_mode_components()
    load_input({type: "UnitreeGo2Odom", config: {...}})
         │
         ▼
② inputs/__init__.py: load_input()
    扫描 inputs/plugins/*.py → 找到 UnitreeGo2Odom 类 → 实例化
         │
         ▼
③ UnitreeGo2Odom.__init__()
    self.odom = UnitreeGo2OdomProvider(unitree_ethernet)  ← 创建 Provider 单例
         │
         ▼
④ UnitreeGo2OdomProvider.__init__()
    super().__init__()  → 创建 mp.Queue()
    self.start()
         │
         ├──────────────────────────────────────────────────┐
         ▼                                                  ▼
⑤ start() 启动两个东西:                         ⑥ 同时启动
   go2_odom_processor(channel, queue)           process_odom()
   ↓ 独立 mp.Process                             ↓ threading.Thread
   ├─ ChannelFactoryInitialize(0, channel)       ├─ while True:
   │  初始化 CycloneDDS 连接                      │    pose = queue.get(timeout=1)
   ├─ ChannelSubscriber(                        │    解析 quaternion → euler
   │   "rt/utlidar/robot_pose",                 │    计算 moving 状态
   │   PoseStamped_                             │    判断 body_attitude
   │  )                                         │    (STANDING / SITTING)
   ├─ pose_subscriber.Init(handler, 10)         │    更新 self.x, self.y,
   │  注册回调: 收到 Pose → queue.put(data)       │    self.moving 等
   └─ while True: time.sleep(0.1)              └──────────────┘
         │                                                  │
         │   mp.Queue (跨进程通信)                             │
         └──────────────────────────────────────────────────┘
                              │
                              ▼
⑦ InputOrchestrator.listen()  ← CortexRuntime 启动时
    async for event in input.listen():   ← 即 FuserInput._listen_loop()
         │
         ▼
⑧ UnitreeGo2Odom._poll()
    await asyncio.sleep(0.1)
    return self.odom.position   ← 直接读 Provider 的属性 (dict)
    # 返回: {odom_x, odom_y, moving, body_attitude, ...}
         │
         ▼
⑨ _raw_to_text(raw_input) → Message
    如果 body_attitude == SITTING → "You are sitting down"
    如果 moving                  → "You are moving"
    否则                        → "You are standing still - you can move"
         │
         ▼
⑩ raw_to_text() → self.messages.append(message)
         │
         ▼
⑪ formatted_latest_buffer()  ← Fuser.fuse() 调用时
    → "INPUT: Information about your location and body pose...\n
       // START\n
       You are standing still - you can move if you want to.\n
       // END\n"

    关键点：

    • Provider 是 @singleton 装饰的单例，Input 和 Background 拿到的是同一个实例
    • 数据采集在独立 multiprocessing.Process 中，通过 mp.Queue 传给主进程的处理线程
    • Channel 名（eth0）通过配置注入，连接宇树机器人的 CycloneDDS 中间件
    • _poll() 只是读内存属性，不阻塞

    为什么需要 Bridge 子进程？¶

    原因：Python GIL + conda 环境隔离

    1. GIL 问题：pyrealsense2 的图像采集是 CPU 密集型操作，如果和 ASR + LLM 在同一进程会严重阻塞
    2. conda 环境隔离：pyrealsense2 需要安装在特定 conda 环境（arx），而 MAGIC 主程序在 .venv 中
    3. 错误隔离：RealSense 相机偶尔会断连/报错，独立进程崩溃不影响主程序，Background 的 bridge loop 会检测到进程退出并报错

    数据交换为什么用文件而不是 IPC？¶

    • 简单可靠：文件系统是 POSIX 标准，没有任何库依赖
    • 原子写入：atomic_write_* 先写 .tmp 再 os.replace()，读端只会看到完整文件
    • 调试友好：可以直接 ls /tmp/magic_realsense_bridge/ 看有没有帧在写入
    • 跨环境兼容：子进程和主进程可以是完全不同的 Python 版本/环境

    hold_last_vision 机制¶

    Tick 1: Voice=无, Vision=新 → formatted_latest_buffer() 消费掉，存入 _held_vision_text
Tick 2: Voice=有, Vision=无 → formatted_latest_buffer() 发现 messages 为空
                                  → 检查 hold_last_vision=true 且 _held_vision 未过期(<45s)
                                  → 复读上一帧的 VLM 描述文本
                                  → LLM 拿到 "Voice + 稍旧的 Vision" 组合

    这解决了时序异步问题：用户说话的那一瞬间，VLM 可能还没完成当前帧的推理，hold_last_vision 确保 LLM 总能拿到一个视觉上下文。

    三、UnitreeGo2State (Background) — 另一种 Background 模式¶

    与 D435 略有不同，UnitreeGo2State 的 run() 方法是空的（只 sleep 60s）。它真正的作用是在 __init__ 中创建 UnitreeGo2StateProvider 单例，供其他组件使用。

    这是一种"通过 Background 声明依赖初始化"的模式——不需要持续运行的循环，只是需要 Provider 被初始化。

    四、通用加载机制总结¶

    配置 JSON5 中的 type 字符串
         │
         ▼
┌──────────────────────────────────────────────┐
│  config.py: _load_mode_components()           │
│                                               │
│  对每个 input/action/background:              │
│    1. 取 raw config 的 type 字段               │
│    2. 调用 load_input() / load_background()    │
│    3. 传参: {**raw, config: add_meta(...)}    │
└──────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────┐
│  例如 inputs/__init__.py: load_input()         │
│                                               │
│  1. 扫描 inputs/plugins/*.py                   │
│  2. 正则匹配 "class <type> (FuserInput)"       │
│  3. importlib.import_module(对应模块)          │
│  4. 找到对应的 Config 类 (如 D435RealSense... │
│     InputConfig)                              │
│  5. 用 config dict 实例化 Config 对象           │
│  6. return <ClassName>(config=config_obj)      │
└──────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────┐
│  Input 实例已创建，存入 ModeConfig.agent_inputs │
│                                               │
│  CortexRuntime._start_orchestrators():        │
│    InputOrchestrator(inputs).listen()          │
│      → 每个 Input 一个 asyncio Task           │
│      → async for event in input.listen()      │
│        → await input._poll() 循环             │
│        → await input.raw_to_text(event)       │
│                                               │
│  CortexRuntime._tick():                       │
│    Fuser.fuse() → 调每个 Input 的              │
│    formatted_latest_buffer() → 拼 LLM prompt   │
└──────────────────────────────────────────────┘

    一句话总结：配置 type 字符串 → 文件系统扫描类名匹配 → importlib 动态加载 → Provider 单例管理数据采集线程 → Input 的 _poll() 轮询 → formatted_latest_buffer() 输出 LLM 可读的格式化文本。

    五、两种模式的对比¶

    维度 Input 自驱动 (UnitreeGo2Odom) Background 驱动 (D435)
    Provider 创建者 Input 自己 Background
    启动方式 Input __init__ 时创建 Provider BackgroundOrchestrator 线程池提交 Background
    采集线程 mp.Process (CycloneDDS) + threading.Thread (处理) subprocess.Popen (bridge 进程) + threading.Thread (bridge loop) + threading.Thread (VLM worker)
    数据共享 Provider 内存属性 (self.position) Provider 内存 (_RealsenseRuntime) + 文件系统 (/tmp/...)
    跨进程通信 mp.Queue (CycloneDDS 进程 → 主进程) 文件 I/O (bridge 进程 → 主进程)
    是否需要 Background 否 是 (必须先启动 Background 初始化 Provider)
    典型场景 轻量传感器 (GPS, Battery, Odom, RTK) 重 IO 设备 (相机, 激光雷达)
