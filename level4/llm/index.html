    LLM 调用与子技能编排层 (src/llm)¶

    文件路径：src/llm/（12 个插件 + 基类 + schema 工具）

    MAGIC 的"大脑皮层"——管理所有与大语言模型的交互，以及核心的两阶段思考架构：先分解用户意图为子任务链，再逐个将子任务交给 LLM 生成具体动作。

    LLM 基类¶

    class LLM(Generic[R]):
    def __init__(self, config: LLMConfig, available_actions=None):
        self._config = config
        # 自动从 available_actions 生成 OpenAI function-calling schemas
        self.function_schemas = generate_function_schemas_from_actions(available_actions)

    async def ask(self, prompt: str, messages=None) -> Optional[R]:
        """发送 prompt 给 LLM，返回类型化响应"""
        raise NotImplementedError

    async def ask_stream(self, prompt, messages=None) -> AsyncGenerator[R, None]:
        """流式返回（默认 fallback 到 ask()）"""

    async def aclose(self):
        """释放 HTTP client + history manager"""

    # LLMHistoryManager.update_history() 装饰器自动管理对话上下文和摘要

    每个 LLM 插件只需实现 ask()。基类自动完成：

    1. Function schema 生成：function_schemas.py 从 AgentAction 的 Pydantic 接口自动提取参数类型，生成 OpenAI 格式的 function 定义
    2. 响应解析：convert_function_calls_to_actions() 把 LLM 返回的 function calls 转为 Action(type=, value=) 对象
    3. 历史管理：通过 LLMHistoryManager.update_history() 装饰器自动管理对话上下文和摘要压缩

    输出类型定义 (output_model.py)¶

    class Action(BaseModel):
    type: str        # 动作类型: "speak", "navigate_location", "grasp_object"...
    value: str       # 动作参数: "你好" / "仓库" / '{"target_name":"bottle"}'

class CortexOutputModel(BaseModel):
    actions: list[Action]    # LLM 返回的动作列表

class VoicePlanStep(BaseModel):
    mode: Optional[str]     # 可选：指定执行此步骤的 runtime mode
    subtask: str            # 自然语言子任务: "导航到仓库"

class VoicePlanOutputModel(BaseModel):
    sub_voices: list[str]            # 分解后的子指令文本列表
    task_plan: list[VoicePlanStep]   # 带 mode 路由的详细计划

class ModeRouterOutputModel(BaseModel):
    decision: Literal["stay", "switch"]  # 停留在当前模式 or 切换
    target_mode: Optional[str]           # 目标模式名
    confidence: float                    # 置信度 0~1
    reason: str                          # 决策理由

    Function Schema 自动生成¶

    function_schemas.py 将每个 AgentAction 的 Pydantic 接口自动转为 OpenAI tool schema：

    # 配置中的 Action 定义:
{
  name: "navigate_location",
  llm_label: "navigate_location",
  interface: "NavigateInput"  # Pydantic model: {location: str}
}

# ↓ function_schemas.py 自动生成:

{
  "type": "function",
  "function": {
    "name": "navigate_location",
    "description": "Navigate to a named location...",
    "parameters": {
      "type": "object",
      "properties": {
        "location": {"type": "string", "description": "The location parameter"}
      },
      "required": ["location"],
      "additionalProperties": False
    },
    "strict": True
  }
}

    每个 tick，MCP tool schemas 被合并进来（加上 mcp_ 前缀以区分内置动作）。LLM 看到的"可用能力列表" = 内置 Action schemas + MCP 外部工具 schemas。

    核心架构：两阶段思考¶

    这是 MAGIC 最重要的设计模式——规划与执行分离：

    用户语音: "去仓库帮我拿瓶饮料然后送到前台"
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  阶段 1: Voice Task Decomposition (轻量级 Planner)        │
│                                                          │
│  voice_task_planner_llm / voice_planner_llm              │
│  模型: qwen3.6-flash (小模型，低成本，~100ms)             │
│                                                          │
│  输入: "去仓库帮我拿瓶饮料然后送到前台"                     │
│  输出: VoicePlanOutputModel                              │
│        sub_voices: [                                     │
│          "导航到仓库",                                    │
│          "抓取饮料瓶",                                    │
│          "导航到前台",                                    │
│          "递给用户"                                       │
│        ]                                                 │
│                                                          │
│  → 存入 voice_task_context (全局动态变量)                  │
│  → 当前指针 = 第 0 步: "导航到仓库"                        │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  阶段 2: 逐子任务执行 (Action LLM)                        │
│                                                          │
│  cortex_llm (主 LLM，如 QwenLLM)                          │
│                                                          │
│  tick N:  当前子任务 = "导航到仓库"                        │
│    prompt 中 Voice 段被替换为: "导航到仓库"                │
│    + 完整的传感器上下文 (位置 / 视觉 / 导航状态 ...)       │
│    → LLM 输出: [navigate_location("仓库")]                │
│    → 执行导航 → 等待到达 → 硬件状态反馈                   │
│                                                          │
│  tick N+1: 到达仓库 → voice_task_context 前进到第 1 步     │
│    当前子任务 = "抓取饮料瓶"                               │
│    → LLM 输出: [speak("开始抓取"), grasp_object("bottle")]│
│    → 执行抓取 → 等待完成 → 状态反馈                       │
│                                                          │
│  tick N+2: 抓取完成 → 前进到第 2 步                        │
│    当前子任务 = "导航到前台"                               │
│    → LLM 输出: [navigate_location("前台")]                │
│    → ...                                                 │
│                                                          │
│  tick N+3: 全部完成 → voice_task_context.task_completed   │
│    → 触发模式切换: grasp → welcome                        │
└─────────────────────────────────────────────────────────┘

    Cortex tick 循环中的关键调度逻辑¶

    来自 src/runtime/cortex.py：

    async def _tick(self, cortex_generation):
    # 1. Fuser 融合所有传感器输入 → 完整 prompt
    prompt = await self.fuser.fuse(self.current_config.agent_inputs, ...)

    # 2. 阶段 1：语音任务分解（仅在有新 Voice 输入时触发）
    planned_subtask = await self._run_voice_task_planner_if_configured(last_input)

    # 3. 获取当前应执行的子任务
    self._advance_voice_task_from_status()           # 根据硬件状态推进子任务指针
    active_subtask = planned_subtask or self._current_voice_task_subtask()

    # 4. 如果有活跃子任务，替换 prompt 中的 Voice 文本为子任务
    if active_subtask:
        prompt = replace_voice_input_in_prompt(prompt, active_subtask)

    # 5. 阶段 2：Action LLM 生成具体动作
    await self._execute_cortex_prompt(prompt, cortex_generation)

    # 6. 检查是否全部完成 → 触发模式切换
    if completion_transition_target:
        transition_result = (completion_transition_target, "voice_task_complete")

    子任务推进基于硬件状态反馈：

    def _advance_voice_task_from_status(self):
    """根据硬件执行状态自动推进子任务指针"""
    # 导航到达目标 → 推进
    # 抓取完成       → 推进
    # 递水完成       → 推进
    # 全部完成       → task_completed = True

    为什么设计两阶段¶

    阶段 1 (Planner) 阶段 2 (Action LLM)
    模型 小模型 (qwen3.6-flash) Qwen LLM (如 qwen3.6-plus)
    成本 极低 (~0.1s) 较高 (~1-3s)
    输入 仅语音文本 完整传感器上下文 (位置+视觉+状态)
    输出 自然语言子任务列表 结构化 function calls
    职责 宏观规划：一句话拆成几步 微观执行：看当前状态，决定具体动作
    触发 有新 Voice 时 每个 tick (持续)

    核心收益： - 规划只需小模型，只在需要做具体决策时调用大模型 - 执行 LLM 每次都拿到最新的传感器上下文，做实时决策 - 硬件状态反馈自动推动任务链前进，不需要 LLM 管理"第几步了" - 子任务失败可重试当前步骤，不影响已完成步骤

    两种 Planner 的区别¶

    系统中有两个独立的 planner 概念：

    voice_task_planner_llm voice_planner_llm
    配置位置 全局 mode_config 顶层 每个 mode 各自配置
    触发时机 有新 Voice 时 每个 tick 检查
    输入 纯语音文本 (+ 长期记忆) Fuser 融合后的完整 prompt (含视觉/状态)
    输出 sub_voices + task_plan (含 mode 路由) sub_voices
    用途 跨模式的多步任务规划 模式内语音分解

    VoicePlannerLLM — 阶段 1 的分解器¶

    voice_planner_llm.py（~200 行）是阶段 1 的典型实现：

    _VOICE_PLANNER_SYSTEM_PROMPT = (
    "You turn one spoken robot command into ordered sub_voices for the action LLM. "
    'Reply with JSON only: {"sub_voices":["..."]}. '
    "Prefer exactly ONE sub_voice when the user expresses a single intent "
    "(pick/grasp/lift an object, greet, reset/home, look left/right, etc.). "
    "Split into multiple sub_voices ONLY when they clearly sequence distinct actions "
    '(e.g. "first turn left then greet", "打完招呼再复位"). '
    "Never split one grasp/pick-up intent into approach vs close-gripper—the executor "
    "already does motion and gripping as one pipeline; keep the user's phrase as one step. "
    "For conditionals (e.g. Chinese '如果…就…', '要是…就…', '…的话就…'), emit sub_voices "
    "in time order: first the prerequisite step (look/move/etc.), then a short imperative "
    "for the consequence (e.g. grasp the bottle)—drop the 'if' wording from sub_voices..."
)

class VoicePlannerLLM(LLM[VoicePlanOutputModel]):
    def __init__(self, config: VoicePlannerLLMConfig):
        super().__init__(config, available_actions=None)  # 不需要 function schemas
        self._client = openai.AsyncClient(
            base_url=config.base_url,    # 默认 http://127.0.0.1:8860/v1
            api_key=config.api_key
        )

    async def ask(self, prompt, messages=None) -> VoicePlanOutputModel:
        # 简单的 chat completion，不用 function calling
        response = await self._client.chat.completions.create(
            model="qwen3.6-flash",
            messages=[system_prompt, ...history, user_prompt],
            extra_body={"chat_template_kwargs": {"enable_thinking": False}},
        )
        # 解析 JSON → VoicePlanOutputModel(sub_voices=["...", "..."])
        return self._parse_content(response.choices[0].message.content)

    关键设计特点：

    • 轻量模型：默认 qwen3.6-flash——快速、便宜，只做分解不做复杂推理
    • 不需要 function schemas：分解器不需要知道有哪些具体动作可用
    • 纯 JSON 输出：{"sub_voices": ["去仓库", "拿饮料"]}，不依赖 function-calling
    • 安全净化：_sanitize_planner_sub_voice() 防止 LLM 把 prompt 指令当子任务输出
    • max_sub_voices：默认最多 5 个子任务，防止 LLM 过度分解

    配置示例¶

    // 全局 voice_task_planner_llm（跨模式多步规划）
voice_task_planner_llm: {
  type: "VoicePlannerLLM",
  config: {
    model: "qwen3.6-flash",
    max_sub_voices: 5,
  }
},

// 模式内 voice_planner_llm（模式内的语音分解）
voice_planner_llm: {
  type: "VoicePlannerLLM",
  config: {
    model: "qwen3.6-flash",
    max_sub_voices: 3,
  }
}

    阶段 2 — 逐子任务执行¶

    阶段 2 由 cortex_llm 负责，通常配置为 QwenLLM（如 qwen3.6-plus）。每个 tick 中，当前子任务的文本替换掉 prompt 中的原始 Voice 段，结合完整的传感器上下文（里程计、视觉、导航状态等），调用 LLM 以 function-calling 方式输出具体的 [Action, Action, ...] 列表。

    LLM 拿到的是"当下的完整画面"——它不需要知道前面执行了几步、后面还剩几步，只需根据当前传感器状态决定眼下做什么。硬件状态反馈自动推进子任务链，LLM 只负责做每个子任务内的微观决策。
