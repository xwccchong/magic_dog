# AttriMem: Attribution-Guided Process Feedback for Agent Memory Construction
2026/7/31 arxiv

需要训练，强化学习

涉及的领域：

+ LLM Agent；<font style="background-color:#FBDE28;"></font>
+ 长期记忆（long-term memory）；
+ 长上下文问答；
+ <font style="background-color:#FBDE28;">强化学习（RL）；</font>
+ 过程奖励与信用分配（credit assignment）。

针对具体的**记忆构建策略学习**：给定一段新的对话，记忆智能体需要决定哪些内容应该被写入核心记忆、情景记忆、语义记忆或程序记忆，以及哪些内容应该被更新、合并、压缩或删除。

<font style="background-color:#FBDE28;">需要训练</font>，训练的内容：记忆智能体先根据历史对话构建外部记忆库；之后，固定的检索器从记忆库中找出相关记录，再由固定的回答模型生成答案。因此，训练目标是改进“记忆怎么建”，而不是训练回答模型本身。

## 解决的问题
**最终答案的正确或错误，无法直接告诉模型是哪一个中间记忆操作、哪一条记忆记录，甚至哪一个词起了作用。 在执行的过程中缺乏GT的监督，无法衡量是否合理（细粒度信用分配瓶颈，只会把整个记忆认为是有效的，但是不知道具体是哪一部分生效）**

## 前人工作
1. 直接检索历史对话

最简单的办法是不专门构建长期记忆，而是直接从历史中检索会话级或 utterance 级内容，例如 RAG 风格的方法。

这种方法的优点是训练成本低，但它通常：

+ 不会主动压缩长期历史；
+ 容易检索出冗余信息；
+ 在长时间跨度和多轮对话中效率较低；
+ 无法学习“什么内容值得长期保留”。
2. 基于启发式规则的记忆系统

主观的启发式规则，缺乏自动探索的过程

[Mem0](/abs/2504.19413?chatId=01a012c2-1c49-7f9a-b67d-080b6588dc40)、[MIRIX](/abs/2507.07957?chatId=01a012c2-1c49-7f9a-b67d-080b6588dc40)、[LightMem](/abs/2510.18866?chatId=01a012c2-1c49-7f9a-b67d-080b6588dc40) 等方法使用人工设计的规则或打分策略来决定：

+ 什么信息应该保存；
+ 什么信息应该合并；
+ 什么信息应该更新；
+ 什么信息应该丢弃。

这类方法能够构建结构化记忆，但规则往往依赖设计者的经验，容易出现**目标错配**：设计者认为重要的信息，不一定是下游问答真正需要的信息，而且规则通常针对特定任务，跨任务泛化能力有限。

3. 用最终任务结果训练记忆策略

另一类工作，例如 [Mem-α](/abs/2509.25911?chatId=01a012c2-1c49-7f9a-b67d-080b6588dc40) 和 [MEM1](/abs/2506.15841?chatId=01a012c2-1c49-7f9a-b67d-080b6588dc40)，使用强化学习直接优化记忆构建策略。

它们根据最终答案是否正确来给奖励：

+ 答案正确，记忆构建轨迹得到高奖励；
+ 答案错误，记忆构建轨迹得到低奖励。

相比手工规则，这种方式的优势是记忆策略可以直接面向下游任务目标进行优化。但问题是奖励非常稀疏：一条长轨迹中有很多记忆操作，却只有一个最终结果，模型很难知道每个操作的贡献。

4. 将最终奖励分配给中间动作

[Mem-T](/abs/2601.23014?chatId=01a012c2-1c49-7f9a-b67d-080b6588dc40) 通过构造记忆动作树，把叶节点上的最终奖励向祖先节点传播。这比只给整条轨迹一个奖励更细致，但它本质上仍然是在**重新分配最终奖励**，并没有增加新的信息，因此仍然无法解释具体哪部分记忆内容帮助了答案。

| **方法** | **监督来源** | **奖励粒度** | **主要问题** |
| :--- | :--- | :--- | :--- |
| 启发式记忆 | 人工规则 | 规则级 | 主观、任务相关、难泛化 |
| Outcome-only RL | 最终答案结果 | 轨迹级 | 奖励稀疏，无法分配信用 |
| Mem-T | 最终奖励的树状传播 | 节点级 | 只是重新分配最终奖励 |
| MemBuilder | 辅助 QA 与检索结果 | 动作级 | 无法区分动作内部的重要 token |
| AttriMem | 最终答案对记忆 token 的归因 | token 级 | 提供更精细的过程反馈 |


## 如何解决问题
### 训练分为两个阶段：
1. **SFT warmup**：先用专家或教师生成的记忆轨迹进行监督微调，使模型学会基本的记忆操作；
2. **GRPO 强化学习**：再根据最终答案奖励和 token-level 过程奖励优化记忆策略。

### 用反事实遮蔽估计 token 贡献
AttriMem 使用 ContextCite 风格的归因方法。具体而言，它把记忆输出中的 token 当作不同的信息源，然后随机遮蔽其中一些 token：

+ 保留某些 token；
+ 删除另一些 token；
+ 将遮蔽后的记忆交给回答模型；
+ 测量最终答案分数如何变化。

如果删除某个 token 后，答案概率明显下降，那么该 token 很可能对答案有正贡献；如果删除它后答案反而变好，说明该 token 可能是噪声或误导信息。

+ 把信用分配从动作级推进到 token 级

此前的方法通常对整条轨迹或整个记忆动作给奖励。AttriMem 进一步把奖励细化到生成记忆的每一个 token。

    - 是否忠实于原始对话；
    - 是否覆盖回答所需的关键事实；
    - 记忆操作是否合理；
    - 是否放入合适的记忆模块；

    - Qwen3-4B。

在 LoCoMo、LongMemEval 和 PerLTQA 上，AttriMem 训练出的记忆都可以被这些回答模型有效利用，说明它学习到的不是只针对某一个回答模型的表面模式。

# ChronoMem: Version Control and Semantic Rollback for Large Language Model Agent Memoy
2026/8/5 arxiv

相关性不大

交叉领域：

+ LLM Agent 的长期记忆；
+ 信息检索与语义搜索；
+ 数据库中的版本控制、事件溯源和状态恢复；
+ 可控、可审计的智能体系统。

## 解决的问题
LLM 智能体通常会把用户事实、偏好、计划、对话摘要和事件轨迹存储到外部记忆系统中。随着多轮交互不断进行，记忆会持续增加、更新、合并甚至覆盖，最终形成一个不断演化的记忆状态。问题在于，<font style="background-color:#FBDE28;">现有系统大多只支持“向前更新”，缺乏一种系统化机制来检查记忆的演化过程、恢复早期状态，或在自然语言层面执行“撤销”。</font>

:::info
**在智能体已经暴露于后续信息之后，如何根据自然语言请求选择正确的历史版本，并恢复整个长期记忆，使后续行为与那个历史时刻保持一致？**

:::

+ **语义定位**：如何把“回到我计划巴黎旅行之前”映射到具体历史版本，而不是要求用户知道内部的版本 ID；
+ **全局还是局部回滚**：是只撤销一条记忆，还是恢复整个记忆状态；
+ **端到端一致性**：回滚之后，后续的问答和摘要不能继续看到回滚点之后的信息。
+ 长期智能体记忆的语义全局回滚

比较特别的是：检索回溯的是历史版本的记忆（区别于历史的真实对话？）

引入了agent的想法，与其多次纠正，不如直接/new或者resume；因为修改如果没有缓存记录是无法完全回档，会有偏差

## 前人工作
1. 主流长期记忆系统：强调“向前演化”

已有的 LLM 记忆工作主要关注：

+ 持续添加新事实；
+ 对记忆进行总结和整合；
+ 检索历史信息；
+ 处理遗忘或记忆衰减；
+ 学习用户偏好；
+ 在长对话中保持事实一致性。

它们评估的是智能体能否从不断增长的记忆中正确检索和利用信息，而不是能否在看到未来信息之后恢复过去状态。文章指出，已有系统一旦把旧记忆覆盖、合并或更新，早期状态往往不会以可访问、可审计的形式保留下来。

2. 已有的回滚机制：范围较窄或依赖内部 ID（限于局部）

这种回滚不就类似于 持续学习中的adapter吗？有任务ID的直接索引，以及通过隐式的重建的，等等，感觉是类似的

+ Vertex AI Memory Revisions

Vertex AI 的 Memory Revisions 支持记忆版本和回滚，但主要是：

    - 针对单条记忆；
    - 依赖内部的 `target_revision_id`；
    - 用户需要知道具体版本标识；
    - 没有公开的系统性评估。

它更像是“对某条记忆进行 ID 级别恢复”，而不是根据自然语言恢复整个全局记忆。

## 如何解决问题
**把智能体长期记忆看成一个带有事件日志、版本、快照和当前指针的版本化状态机。**

将自然语言回滚分解成两个步骤：（一个是选择，另外一个是如何恢复）

1. **自然语言请求 → 目标版本选择**；
2. **目标版本 → 确定性状态恢复**。

### 每次写入都创建一个完整版本
ChronoMem 采用 **commit-on-write** 策略：

+ 每次记忆写入都会追加一个不可变事件；
+ 每次写入都会产生一个新的版本；
+ 每个版本对应一个完整的长期记忆快照；
+ 系统维护一个 `HEAD` 指针，表示当前激活版本。

### 不直接检索完整快照，而是建立“版本描述索引”
ChronoMem 并不是在所有完整记忆快照中直接搜索，而是在这些**版本变化描述**上搜索。这样做可以让搜索规模主要取决于版本数量，而不是完整快照的大小；只有选定目标版本之后，系统才加载快照内容。

### 使用混合检索选择历史版本
自然语言回滚请求 $q$ 会经过一个两阶段检索流程：

1. **词法检索**：使用 SQLite FTS5 和 BM25 风格的排序；
2. **稠密检索**：对版本描述进行向量化，通过近似最近邻搜索找到语义相似版本；
3. **RRF 融合**：将词法和语义检索的排序结果融合；
4. **交叉编码器重排序**：对候选版本进行更精细的相关性判断；
5. 选出目标版本 $\hat v$。

### 用确定性操作恢复全局状态
步骤包括：

1. 读取目标版本的快照；
2. 将本地长期记忆恢复为该快照；
3. 将 `HEAD` 设置为目标版本；
4. 截断目标版本之后的版本；
5. 同步检索后端中的记忆索引。

回滚后，系统要求满足一个接口不变量：

所有后续记忆读取都必须限定在当前 `HEAD` 对应的版本范围内，不能再看到回滚点之后的信息。

# ConvMemory v3: A Validity Context Layer for Conversational Memory via Target-Conditioned Relation Verification
2026/6/25 arxiv

需要训练 证据头

聚焦于**对话式长期记忆（conversational memory）检索中的“记忆有效性判断”问题**：一条记忆可能与用户当前问题高度相关，但已经被后续对话更新、纠正或取代，因此“相关”并不等于“仍然正确”。ConvMemory v3 的核心目标，是在已有记忆检索之后判断：**针对当前查询所关心的具体命题，某条旧记忆是否已经被后来的记忆推翻**。



历史的情况是：

传统记忆系统主要解决的是：

“过去哪条记忆与当前问题最相关？”

但本文认为，长期对话还需要解决另一个问题：

“这条相关记忆现在是否仍然有效？”

这一点与TMM中进行充分性检验一致，而且是更为合理的方向

<font style="background-color:#FBDE28;">仅靠语义相似度可能仍然把它排在前面；但从当前状态看，它已经被后续记忆取代。论文将这种现象称为</font>**<font style="background-color:#FBDE28;">relevance 与 validity 的分离</font>**<font style="background-color:#FBDE28;">：相关性检索负责找到记忆，有效性层则负责判断它是否仍然成立。</font>

## 前人工作
### ConvMemory v1：高召回检索和轻量重排
前一篇 [ConvMemory v1](/abs/2605.28062?chatId=01a01d15-33d0-787e-bd07-0a8cba177243) 主要构建一个高召回的记忆检索流水线：

1. 使用稠密检索获得较大的候选池；
2. 对候选记忆进行轻量学习式重排；
3. 关注如何把相关记忆找回来。

### ConvMemory v2：保护召回率的 Top-10 证据重排
[ConvMemory v2](/abs/2606.10842?chatId=01a01d15-33d0-787e-bd07-0a8cba177243) 在 v1 的基础上，对受保护的 Top-10 候选进行证据重排：

+ v1 先提供候选池；
+ v2 只重新排列已经进入保护集合的 Top-10；
+ Recall@10 通过设计保持不变；
+ 目标是改善 MRR 和 H@1，而不是识别记忆是否过时。

因此，v2 改善的是“候选记忆的排序”，而不是“某条记忆是否被后来的信息推翻”。v3 继续把 v1/v2 作为固定的底层检索路径，在其后增加有效性判断层。

**基于时间位置的规则**：认为较新的记忆更可能有效。

**普通 NLI 或事实矛盾检测**：判断两句话是否蕴含、矛盾或中立，但如果不指定目标命题，就可能把“同一个人但不同属性”的事实混为一谈。

**相关性重排模型**：相关性模型擅长回答“哪些记忆与查询相关”，但不擅长判断“哪些相关记忆已经失效”。

## 如何解决问题
它不是直接修改或删除旧记忆，也不是修改语言模型参数，而是在检索结果上增加有效性证据。这样可以保留原始记忆，便于审计，同时让下游智能体知道某条候选记忆可能已经过时。

### 双证据目标条件化门控
核心机制称为**target-conditioned dual-evidence gate**。

对于一个目标记忆 $t$ 和一个候选源记忆 $s$，模型判断：

源记忆 $s$ 是否直接且具体地推翻了目标记忆 $t$？

模型使用两个 slot heads：

1. 基于 MiniLM 的 cross-encoder；
2. 基于 NLI 初始化的 DeBERTa-v3 cross-encoder。

只有当两个模型都认为源记忆确实针对目标命题构成推翻时，slot score 才会较高。这种乘法是保守策略，可以压制“主题相同但没有真正更新关系”的假阳性。

### 事件和操作证据门控
仅仅判断源记忆是否针对目标命题还不够，源记忆还必须：

+ 是一个更新或冲突事件；
+ 其操作类型确实是 overturn，而不是补充、共存或无关。

### 对多个源记忆进行 noisy-or 聚合
一个目标记忆可能被多个后续源记忆推翻，因此 v3 用 noisy-or 聚合多个证据：

$$   
\operatorname{noisy\_or}(x_1,\ldots,x_n) = 1-\prod_i(1-x_i)  
$$

处理过程是：

1. 同一个源记忆产生的多个 edge score 先聚合成 source score；
2. 多个源记忆的 source score 再聚合成目标记忆的 invalidity score；
3. 最终决定目标记忆是否应被标记为可能过时。

# MESA: Task-Adaptive Multi-Structure Evidence Selection for Long-Horizon Agent Memory
通过对五种记忆结构的全部组合进行实验发现，最优配置通常既不是单一结构，也不是全部结构，而是一个**随查询和任务变化的中间子集**。

<font style="background-color:#FBDE28;">相当于把动态混合专家的思路引入记忆检索或者记忆结构构造</font>

## 解决的问题
长时程智能体往往会经历数百个交错的“思考—行动—观察”步骤。之后回答一个问题时，关键证据可能隐藏在很早之前的某个工具输出、代码片段或状态变化中。因此，核心问题不是单纯地“让模型看更长的上下文”，而是：

**面对一个具体查询，应该从哪些记忆结构中检索证据，并且如何组合这些证据？**

文章认为，已有方法通常面临两个极端：

1. **只使用一种记忆结构**：可能找不到某类必要证据；
2. **每次都读取所有记忆结构**：虽然召回率较高，但上下文成本大，也会引入冗余和噪声。

## 前人工作
1. 直接使用长上下文

长轨迹会带来两个问题：

    - 上下文成本很高；
    - 关键证据容易被大量无关信息淹没，即使模型支持很长的上下文，也不一定能稳定找到它。

文章将这种方法称为 `Long-context` baseline，并指出，截断或压缩虽然可以降低成本，却可能删除之后真正有用的细节。

2. 使用单一的记忆结构

另一类工作会把历史转化成某一种结构，例如：

+ **文本摘要**：保留整体任务状态、重要事件和子目标变化；
+ **时间存储**：保留按步骤排列的原始动作和观察；
+ **向量数据库**：通过语义相似度查找相关步骤；
+ **知识图谱**：通过实体和关系进行多跳检索；
+ **原始情节轨迹**：尽可能保留动作和观察的原始文本。

这些结构各自擅长不同类型的查询，但也各有缺陷：

| 记忆结构 | 优点 | 主要局限 |
| --- | --- | --- |
| 摘要 | 提供全局上下文和状态变化 | 可能丢失精确命令、数值和步骤细节 |
| 时间存储 | 精确定位某个步骤或时间范围 | 查询没有明确时间锚点时不容易检索 |
| 知识图谱 | 适合实体、关系和因果链路 | 缺乏完整的步骤级顺序信息 |
| 向量数据库 | 能找到语义相近的局部片段 | 可能返回语义相似但任务无关的步骤 |
| 原始轨迹 | 保留完整表面形式和局部上下文 | 噪声多，关键线索容易被淹没 |


这些方法的共同问题是：<font style="background-color:#FBDE28;">即使系统内部维护了多种索引或结构，</font>**<font style="background-color:#FBDE28;">读取策略通常是固定的，或者只选择一个结构</font>**<font style="background-color:#FBDE28;">，而不是根据当前问题动态选择多个互补结构。</font>

3. 固定地融合所有记忆结构

比较先进的混合记忆方法会同时查询多个结构。例如，[Hindsight](/abs/2512.12818?chatId=01a01d44-93c4-7f2f-9cec-d1ce53f16ecc)并行使用语义匹配、BM25、图遍历和时间过滤，再通过排序融合得到结果。

这种方法的优点是覆盖面广，但缺点是：

    - 每个问题都读取同样的结构；
    - 许多结构对当前问题可能没有帮助；
    - 证据数量和上下文长度持续膨胀；
    - 冗余信息可能干扰答案模型。

文章将其概括为“read-all”策略：最大化召回，但没有针对查询的选择能力。

4. 只路由到一个最佳结构

另一种思路是为每个查询选择一个最合适的结构。例如，有些方法会在摘要、图、层级结构或外部知识源之间进行单路由。

这种方法降低了成本，但表达能力受限。一个问题可能同时需要：

+ 摘要提供全局状态；
+ 时间存储提供准确步骤；
+ 图结构补充实体关系；
+ 原始轨迹提供精确代码或错误信息。

如果只能选择其中一个结构，就无法组合这些互补证据。文章的关键判断是：

真正合适的策略不是“只选一个”，也不是“全部都选”，而是选择一个与当前查询需求匹配的多结构子集。

## 如何解决问题
MESA的基本流程是：

1. 离线地把每条智能体轨迹转换成五种记忆结构；
2. 查询到来时，分析问题及其上下文；
3. 选择一个非空的记忆结构子集；
4. 分别从选中的结构中检索证据；
5. 将证据合并；
6. 交给一个冻结的答案模型生成最终答案；
7. 只优化“选择器”，而不改变记忆构建器、检索器和答案模型。

五种结构分别是：

+ $S$：Summary，摘要记忆；（提供**全局背景和任务状态**）
+ $T$：Temporal Store，时间存储；（保留原始的动作—观察序列，并根据问题中提到的步骤、范围或时间线索直接定位相关步骤）
+ $G$：Knowledge Graph，知识图谱；（知识图谱从轨迹中抽取实体—关系—实体三元组，并且尽可能把关系连接回原始轨迹步骤）
+ $V$：Vector Database，向量数据库；（向量数据库将每个动作—观察步骤编码为向量，按照查询与步骤之间的余弦相似度检索最相关的步骤。它主要用于发现**语义上相近的局部证据）**
+ $R$：Raw Episodic Trace，原始情节轨迹。（原始轨迹被切成有重叠的窗口，再通过BM25进行匹配。它保留精确的表面形式）

### 通过答案级反馈学习，而不是依赖人工标注的最佳结构
实际数据中通常没有“这个问题应该使用摘要和图结构，但不应该使用向量结构”这样的标签。

因此，MESA不要求人工标注正确的结构组合，而是：

1. 选择一个结构组合；
2. 检索证据并生成答案；
3. 根据最终答案是否正确获得反馈；
4. 用答案级反馈更新选择策略。

这是一种弱监督或稀疏反馈设置。

### Prior-guided harness optimization
如果直接在所有可能的选择策略上进行盲目搜索，搜索空间会非常大，而且答案级反馈非常粗糙。

因此，MESA预先规定了20种“先验方向”，将策略搜索分成几类：

+ 根据问题能力推断需求；
+ 根据领域和任务推断需求；
+ 根据关键词和标识符推断需求；
+ 估计不同记忆结构的边际价值；
+ 进行前向选择；
+ 识别互补证据；
+ 根据证据相关性、覆盖度和冗余度进行选择；
+ 设置置信度回退和成本控制。

这些先验并不直接规定“哪个问题应该选哪个组合”，而是约束搜索应该沿什么方向改进。

### Upper Confidence Bound (UCB)-guided scheduling
+ 第一项偏向已经产生高质量策略的方向；
+ 第二项鼓励探索尚未充分尝试的方向。

## 解决的问题
传统的视觉问答通常只需要处理一个问题和一组图像；但长期记忆智能体面对的是持续增长的交互历史。相关证据可能分散在不同会话、不同时间和多张图像中，而且还可能出现后续修正、实体指代和过时信息更新等情况。文章指出，系统需要同时解决远距离信息检索、图文绑定、时间更新、冲突处理、多跳证据组合以及无法回答时的拒答问题。

## 前人工作
1. 直接使用长上下文
2. 外部记忆与固定检索

另一类方法把历史交互保存为：

    - 文本摘要；
    - 结构化笔记；
    - 层次化记忆；
    - 记忆图；
    - 文本或图像向量索引。

3. 查询时的智能体式检索

更灵活的方法允许模型在查询时：

    1. 改写查询；
    2. 多轮检索；
    3. 根据中间结果继续搜索；
    4. 交错进行检索和推理。

这类方法比固定RAG更自适应，但代价是增加在线模型调用和检索轮数，导致延迟和token成本上升。文章将其概括为：它们把访问规划留在查询时解决，因此每个问题都可能需要重复进行复杂规划。

## 如何解决问题
PMMC由三个角色组成：

1. **Questioner**：根据当前已经积累的交互历史，预测可能出现的未来问题；
2. **Planner**：为每个问题规划一个多模态记忆访问程序；
3. **Doubter**：实际执行这个程序，检查它是否找到了正确类型和数量的证据，并要求修正不可靠的程序。

这些通过验证的问题—程序对被存入一个 **Question Bank**。查询到来后，系统只需要：

1. 将新问题与Question Bank中的候选问题匹配；
2. 选择对应的记忆程序；
3. 在当前可见的历史记忆上重新执行程序；
4. 将程序找回的原始文本、上下文和图像交给回答模型；
5. 如果没有合适路线或证据不足，则退回到原生多模态RAG。

<font style="background-color:#FBDE28;">Question Bank保存的是</font>**<font style="background-color:#FBDE28;">访问策略，而不是答案缓存</font>**<font style="background-color:#FBDE28;">。编译阶段产生的临时答案、私有证据支持、规划理由和评估标签都会被删除；查询时程序会重新在当前可见的记忆上检索，因此也可以找到编译之后新出现的有效记忆。</font>

从“query-time reasoning”向“consolidation-time compilation”的转变

从本质上看，也是混合专家，明确了不同的检索查询类型会对应不同的问题，具有针对性地去处理；而不是一概而论了；

### 用实际执行结果验证规划，而不是只看文字上是否合理
Planner给出的计划可能在文字上看起来合理，但实际执行时可能检索不到证据，或者缺少所需模态。PMMC因此让Doubter基于实际执行轨迹进行检查。

一个程序只有在以下条件同时满足时才算准备就绪：

+ 程序执行成功；
+ 找到了非空证据；
+ 覆盖问题需要的模态；
+ 使用了问题所需的检索能力；
+ 证据数量达到要求。

如果失败，Doubter会给出结构化修正指令，例如增加视觉检索、扩展时间上下文、访问原始图像或增加检索深度，然后Planner重新生成程序。

TMM: Tree-structured Multimodal Memory System for Long-term Conversational Agents

#### 问题一：记忆构建时的信息损失
对记忆进行压缩，出现灾难性遗忘；丢失关键信息



#### 问题二：多模态记忆检索时的模态隔离
文本问题去检索文本，图片问题去检索图片，二者之间缺少明确关联。记忆中是独立存储，文本对应文本记忆，图片对应图片记忆



#### 问题三：**大语言模型/视觉语言模型智能体的长期记忆问题**
当对话或历史文档不断增长时，如何在有限的上下文和推理预算下，既保留关键证据，又避免检索噪声、信息丢失和成本线性增长。



#### 前人工作


+ MemGPT
    - 把长期对话记忆看作一种外部存储，并通过分层管理、检索和上下文调度来突破有限的上下文窗口。
    - 相当于开了一个mem buffer，用来回放或者检索，类似于ER方法

文本记忆方式：

1. **事实抽取**  
从对话中抽取“用户喜欢什么”“用户养了什么宠物”等结构化信息，并存入向量数据库。
2. **层次化记忆**

先定位相关会话，再从会话中寻找相关事件或事实，避免在所有历史记录中进行平面检索。

3. **知识图谱或实体关系记忆**  
将人物、事件、时间和关系组织成图结构，方便多跳推理。

多模态工作通常会为图片建立单独的记忆，例如：

1. 把图片转换成 caption，再进行文本检索；
2. 使用图像 embedding 进行相似图片检索；
3. 将图片和文本分别存储，在查询时根据输入模态选择对应的检索路径。



##### 存在问题：
+ **依赖摘要或 caption**：caption 可能没有写出图片中的关键细节；
+ **文本和图片分开检索**：即使两类证据都被检索出来，也不一定知道它们之间的语义对应关系。



#### 记忆构建	
相当于编码器或者预处理部分

##### 结构化事件抽取（类似于数据预处理，和原子技能分解部分类似）
TMM 首先把一段多轮对话转换成结构化事件。每个事件包含：

+ 事件内容；
+ 事件发生时间；
+ 事件对应的原始对话轮次 ID。

例如，原始对话：

用户：我上周五收养了一只叫 Lumi 的马尔济斯犬。  
助手：她看起来很可爱。

可以抽取为：

+ 内容：用户收养了一只名叫 Lumi 的马尔济斯犬；
+ 时间：上周五；
+ 原始轮次 ID：对应原对话中的某一轮。

这里最关键的是**保留原始轮次 ID**。它相当于一个“回溯指针”，使得结构化事件不仅保存摘要，还能够回到原始对话中查找更详细的信息。

###### 保留原始对话轮次
与很多只保留摘要的系统不同，TMM 会将原始对话轮次无损地保存在会话节点下。

因此，记忆中同时存在两种粒度：

+ **结构化事件**：便于快速检索；
+ **原始对话**：用于需要时恢复细节。

这形成了“先摘要定位、后原文补充”的机制。



##### 构建人物画像（这个部分有什么作用呢？用来维持更长久的记忆吗？使用gpt时确实会有这种感觉，之前历史的信息也会有，但是对于回答其实有一定的影响，因为存在一个无上下文的提问时，会突然蹦出我很久之前和他对话的内容，相关的东西，然后基于这个信息来与当前的输入结合回答我的问题，出现次数较少，1-2次）
维护人物级别的长期画像，包括五类信息：

1. 个人信息；
2. 性格和特征；
3. 人际关系；
4. 兴趣和活动；
5. 生活状态。

人物画像主要用于处理关于用户或角色本身的问题，也可以作为后续推理的背景信息。



###### 建立统一的视觉记忆
对于每张图片，TMM 不仅保存图片本身和 caption，还使用一个融合式多模态编码器，将以下内容编码到同一个语义空间：

+ 包含图片的对话轮次文本；
+ 图片 caption；
+ 图片像素。

文中使用的融合表示维度为 1,536。这样，图片的表示不再只依赖视觉内容，也包含了图片在对话中的语境。



###### 对图片添加对话相关属性标签
使用视觉语言模型为每张图片生成一个最多包含一个属性的标签；生成标签时，模型不仅看图片和 caption，还会参考图片所在对话轮次前后各三轮的上下文。

属性标签**不直接参与视觉检索打分**，而是在最终回答阶段作为补充证据提供给生成模型



#### 记忆检索
###### 层次化文本检索
减小上下文长度，过滤有效部分，逐层聚焦

+ 检索相关会话

系统首先根据查询和会话主题的相关性选择若干会话。相关性由三部分融合得到：

    - 字符串匹配；
    - BM25；
    - 语义相似度。

默认情况下，系统至少选择 4 个、最多选择 8 个会话。

+ 检索相关事件

在选中的会话中，系统再对所有事件进行排序，并选出 top-$k$ 个事件。

这样做的好处是：

    - 先缩小检索范围；
    - 减少无关会话引入的噪声；
    - 保留会话层面的时间和语义结构。

###### 记忆充分性检查与细节回溯
当前记忆抽象信息不完整时，就需要回溯原始对话获取完整信息

检索摘要 → 判断证据是否充分 → 不充分则回溯原始轮次 → 补充细节 → 回答



+ 这个地方相当于经验回放，但是经验回放是默认直接进行的，但是这里还是进行了衡量之后才考虑回放；而且这里的回放是有指向性的，因为记录了原始对话的ID

###### 跨模态视觉检索
对于视觉记忆，TMM 使用统一的文本—图像语义空间。

如果查询带有图片，系统将以下内容共同编码：

+ 用户的问题；
+ 查询图片；
+ 查询图片的文本描述。

如果查询只有文本，也可以直接使用问题文本去检索图片记忆。

例如，文本查询：

找出和查询图片属于同一植物种类的所有照片。

系统可以根据问题语义和图片内容，直接从视觉记忆中找到相关图片，而不必先将所有图片转成 caption 再进行纯文本匹配。

1. 文本查询也能够访问视觉记忆；
2. 图像检索同时考虑图像相似性和问题意图。

### Visual Context Record Memory: Empowering Efficient Memory for Vision-Language Models
比较特殊的是考虑到跨对话之间有效信息的关联

**大语言模型/视觉语言模型智能体的长期记忆问题**：当对话或历史文档不断增长时，如何在有限的上下文和推理预算下，既保留关键证据，又避免检索噪声、信息丢失和成本线性增长。

###### 问题一：Token 预算随历史线性增长
传统系统通常把历史保存成文本记忆，例如：

+ 对每轮对话抽取若干事实；
+ 更新已有记忆；
+ 把相关记忆检索出来；
+ 将文本记忆重新放入上下文。

历史越长，需要存储、更新和读取的文本越多，导致：

+ 记忆构建阶段需要频繁调用 LLM；
+ API 调用次数和输入输出 token 增加；
+ 推理延迟变高；
+ 检索结果仍然可能超过上下文预算。

###### 问题二：关键证据在长上下文中逐渐“扩散”
为了提高召回率，系统往往检索较多候选片段。但候选片段中会混入：

+ 与问题相关性较弱的内容；
+ 重复事实；
+ 被切碎的对话片段；
+ 缺少时间信息或指代关系的片段。

结果是，真正回答问题所需的证据会被大量噪声淹没。即使正确证据已经被检索出来，模型也可能无法准确定位它。



#### 前人工作
###### 直接使用长上下文（经验回放）
最直接的办法是把尽可能多的历史对话全部放入模型上下文。

这种方法的优点是不会主动删除信息，但问题也很明显

+ 成本和延迟随上下文长度增加；
+ 上下文窗口仍然有限；
+ 模型不一定能有效利用所有输入；
+ 关键内容可能出现“lost in the middle”现象，即信息位于长上下文中间时更容易被忽略。

###### 文本形式的外部记忆和 RAG（现在的方法，隐式记忆）
目前更常见的是把历史转成外部文本记忆，再进行检索。例如，[Mem0](https://www.alphaxiv.org/abs/2504.19413?chatId=019fc574-aaef-7271-b0cd-f3d6aaeb8198)采用增量式事实抽取和记忆更新，[LightMem](https://www.alphaxiv.org/abs/2510.18866?chatId=019fc574-aaef-7271-b0cd-f3d6aaeb8198)强调分层和离线记忆整合，而 [True Memory](https://www.alphaxiv.org/abs/2605.04897?chatId=019fc574-aaef-7271-b0cd-f3d6aaeb8198)更加侧重检索阶段的记忆组织。

```plain
历史对话
   ↓
事实抽取、摘要或记忆卡片构建
   ↓
向量检索 / 关键词检索 / 重排序
   ↓
拼接文本记忆
   ↓
LLM 生成答案
```



仍有几个问题：

1. **存储阶段可能已经丢失信息**  
如果某个事实在写入记忆时没有被抽取出来，后面即使查询与它相关，也无法恢复。
2. **检索结果仍然是线性文本**  
检索出多少内容，通常就需要消耗多少文本 token。
3. **固定 Top-****$K$**** 不适合所有问题**  
简单问题可能只需要一个片段，复杂的多跳问题可能需要很多片段。固定 $K$ 很难同时兼顾召回率和压缩率。
4. **文本记忆容易碎片化**  
一个完整事实可能分散在不同对话轮次中，导致时间、主语和因果关系丢失。

###### 将文本渲染成图像进行压缩
把文本渲染成图片，再交给视觉语言模型读取。例如，[MemOCR](/abs/2601.21468?chatId=019fc574-aaef-7271-b0cd-f3d6aaeb8198)使用视觉布局来保存和压缩长期记忆。

这类方法的核心优点是：图片可以通过空间布局表达信息，并且可以在一定程度上压缩文本。

+ 论文提出文转图依旧有缺陷：

视觉记忆方法仍有两个不足：

    - 如果在渲染之前没有进行充分检索，图片中仍然会包含大量冗余内容；
    - 如果所有文字都用类似的视觉密度表示，关键证据和普通细节很难区分；
    - 某些方法依赖强化学习训练，训练成本高，也可能出现模型分布偏移问题。

#### **Hierarchical Evidence Prospecting，HEP：层次化证据探测（检索）**
###### 异构信号聚合
对于每个历史片段，计算：

+ 语义向量相似度；
+ 词法匹配分数；
+ 相关性重排序分数。

先对三种分数分别进行 z-score 标准化，再进行加权融合：

这样做的原因是，不同检索器的分数范围和分布可能不同。如果直接相加，数值方差较大的信号可能会主导最终结果。

这一步相比单独使用向量检索更加稳健：

+ 语义匹配可以处理表达方式不同但含义相近的内容；
+ 词法匹配有助于保留实体、日期和专有名词；
+ 重排序器可以进一步判断问题与历史片段之间的相关性。

###### 分层置信度路由
使用最大重排序分数作为检索置信度指标

+ 如果 $r$ 较低，说明检索器无法明确判断哪个片段最相关，此时保留更多候选；
+ 如果 $r$ 较高，说明匹配较明确，可以只保留较少候选。

###### 自适应悬崖剪枝
候选片段按融合分数排序后，观察相邻候选之间的分数下降。如果前几个候选分数很高，后面的候选突然出现明显下降，就说明这里存在一个“分数悬崖”。

如果第 1 到第 5 个片段都很相关，而第 6 个片段之后相关性突然大幅下降，就没有必要继续渲染所有尾部片段。

效果：更少的渲染与检索，性能持平甚至提升



#### DSR：如何把关键证据变成高密度视觉记忆
###### 语义事实抽取（数据预处理+编码）
候选文本可能仍然很长，因此 VCRM 将它切分成多个文本块

然后让视觉语言模型根据问题 $q$，从每个文本块中提取相关事实

提取后的事实不仅包含答案实体，还尽量保留：

+ 时间信息；
+ 事件顺序；
+ 主体和对象；
+ 多跳推理所需的连接信息；
+ 与问题直接相关的关键词和数字

###### 密度差异化渲染（这个是相较于memocr的改进？）
得到结构化事实集合 $F$ 后，VCRM 使用轻量级渲染器将其生成一张二维图像 $V$。

它不是让每个词占用同样大小的空间，而是根据语义重要性分配视觉密度：

+ 查询相关关键词：更大字体；
+ 日期、时间和数字：更醒目；
+ 关键实体：加粗或放在显著位置；
+ 辅助信息：使用小字体，放在边缘或次要区域。

因此，图片内部的信息密度是非均匀的。

### Mem0
核心问题：**LLM 的上下文窗口是有限的，而且模型本身不会自动跨会话保存信息。**

1. 忘记用户偏好；
2. 重复询问已经知道的问题；
3. 前后回答矛盾；
4. 随着历史增长，推理成本和延迟不断上升。

**之前两篇文章都不是解决这个问题的？**



Mem0 的核心思想不是保存完整对话，也不是简单地检索原始文本，而是把对话逐步转换成**紧凑、可更新的长期记忆条目**。（持续学习，和我现在的prototype很像？）

#### 大模型记忆能力的关键能力
真正需要的是一个独立的记忆系统，能够：

+ 选择性地保存重要信息；
+ 合并重复或相关的信息；
+ 更新过时信息；
+ 删除被新信息推翻的内容；
+ 在回答问题时只取回相关记忆。

#### 前人工作
##### 直接使用完整上下文
信息最完整，不需要额外设计记忆抽取模块，但是token耗费增长，推理速度慢，上下文长度不可能为无限（有限算力下）

##### 使用 RAG 检索原始对话片段
另一种思路是把对话切分成固定长度的 chunk，建立向量索引，提问时检索最相关的一个或两个片段。

这比完整上下文更节省计算，但存在两个问题：

1. chunk 可能太大，包含大量噪声；
2. chunk 可能太小，导致关键事实被切散，跨片段关系难以恢复。

思源的论文中断崖式剪枝就合理的解决了这个问题，**但是前提是有置信分数量化**

##### 传统或专门设计的记忆系统
+ LoCoMo：结合会话摘要、长期观察结果和时间事件图；
+ ReadAgent：把长文本分段、生成 gist，再根据问题回查原文；
+ MemoryBank：存储对话、事件摘要和用户画像，并通过记忆强化与衰减机制进行更新；
+ MemGPT：借鉴操作系统的 RAM/磁盘结构，由模型主动在主上下文和外部存储之间换入换出内容；
+ A-Mem：把记忆组织成相互连接、可持续演化的笔记；



#### 如何解决问题
**对话发生时抽取重要事实 → 与历史记忆对齐 → 合并或修正记忆 → 查询时只检索相关记忆 → 将少量记忆交给 LLM 生成答案。**

##### 记忆抽取（编码，预处理）
每当出现一组新的消息，例如用户消息和助手回复，Mem0 会同时使用：

1. 整个会话的摘要；（对应全局的主题）
2. 最近若干条消息；（最近的上下文信息，提供依据，最近的语境）
3. 当前的新消息对。（最新的输入）

##### 记忆更新（编码，检索）
对于每个候选事实，系统先通过向量检索找到最相似的旧记忆，取 10 条相似记忆。然后把候选事实和旧记忆交给 LLM，通过 function calling 选择四种操作之一：

+ **ADD**：没有相似记忆，新增；
+ **UPDATE**：已有相关记忆，但新信息更完整或更丰富；
+ **DELETE**：新信息与旧信息冲突，移除旧信息；
+ **NOOP**：信息已经存在，或者不值得修改
+ 单纯依赖LLM来选择操作类型（prompt编写很关键）

#### Mem0ᵍ 则进一步引入了**图结构记忆**。（更合理，但是复杂一些）
它把记忆表示成有向标记图：

+ 节点表示实体，例如人物、地点、事件或属性；
+ 边表示实体之间的关系，例如 `lives_in`、`prefers`、`owns`；
+ 节点还包含类型、embedding 和创建时间；
+ 边可以表示关系的时间和有效性。

存储空间更小，节点表示更加结构化

##### 图记忆的构建
两个 LLM 模块：

1. **实体抽取器**：识别人、地点、物品、事件、偏好等实体；
2. **关系生成器**：为实体之间生成关系三元组。

加入新事实时，系统会：

+ 对新实体计算 embedding；
+ 搜索已有的相似节点；
+ 复用已有节点或创建新节点；
+ 建立新关系；
+ 检测冲突关系；
+ 将过时关系标记为无效，而不是简单物理删除。

保留无效关系有助于进行时间推理，例如判断一个偏好是现在的，还是过去曾经成立。

+ **实体中心检索**：先找问题中的关键实体，再沿着实体的入边和出边扩展相关子图；
+ **语义三元组检索**：将整个问题编码成 embedding，与图中的关系三元组进行相似度匹配。

前者适合“关于某个人或事件的关系查询”，后者适合更宽泛的语义问题

### MemGPT（即插即用方法）
传统 LLM 的输入上下文窗口可以理解为一块容量有限的“工作内存”。当对话变长或文档变大时，会出现三个问题：

1. **历史信息被截断**：模型只能看到最近的一部分对话。
2. **摘要会丢失细节**：把过去内容压缩成摘要后，具体事实、偏好或事件可能消失。
3. **长上下文不一定真正有效**：即使模型支持更长输入，也可能更难利用位于上下文中间的信息。
+ 核心思想

实现一种类似“虚拟内存”的机制：让模型继续使用固定长度的上下文窗口，但可以把更多信息暂时存放到外部存储中，需要时再取回来。**把 LLM 的有限上下文当作 RAM，把外部存储当作磁盘，让 LLM 自己决定什么时候换入、换出和搜索信息。**

#### 前人工作
##### 直接扩大上下文窗口（保留完整的上下文）
把更多内容一次性放入模型输入（使用更加高效的注意力机制）。但它有两个根本限制：

+ Transformer 的自注意力通常会随着序列长度增加而显著增加计算和显存成本；
+ 更长的输入不等于更好的信息利用，模型可能仍然无法稳定找到位于上下文中部的关键信息。

##### 截断、摘要和压缩
只保留最近的对话，或者对已经离开上下文窗口的历史进行递归摘要。这样可以控制输入长度，但摘要本质上是有损的

+ 不重要的信息可能被错误删除；
+ 细粒度事实可能在多次摘要后消失；
+ 模型无法再访问完整的原始对话。

##### 检索增强（开环，无反馈）
在长文档问答中，常见办法是先用检索器找出最相关的若干文档，再把这些文档交给 LLM 阅读。这比把整个语料库放入上下文更高效

+ 检索器只返回固定数量的前 $K$ 个结果；
+ 检索过程通常由系统预先完成，模型本身不能根据当前推理结果继续翻页、改写查询或执行多步检索。 

##### 给 LLM 增加工具和记忆
让 LLM 调用外部工具、搜索信息或执行动作

#### 如何解决问题
##### 两级记忆结构
MemGPT 将记忆分成“主上下文”和“外部上下文”。

**主上下文** 是真正会被送入 LLM 的内容，包括：

+ 系统指令；
+ 可读写的 working context；
+ 按先进先出方式保存的 FIFO 对话队列。

**外部上下文** 位于模型输入之外，包括：

+ **recall storage**：保存完整的历史消息；（注意，这里保留的是完整的历史信息，应该是非常繁杂庞大的）
+ **archival storage**：保存任意长度的外部文本，例如 Wikipedia 文档或上传的资料。

##### Queue Manager 管理上下文压力
当新消息到来时，Queue Manager 会把用户消息和模型输出加入 FIFO 队列，并把消息写入 recall storage。

当上下文接近容量上限时，系统先发送一个 **memory pressure** 警告，让 LLM 主动保存重要信息，例如：（重要信息就是用户画像+摘要？）

+ 用户的姓名；
+ 用户的偏好；
+ 某个重要事件；
+ 当前任务的关键中间结论。

如果上下文继续增长并超过 flush threshold，系统会驱逐一部分旧消息，同时根据旧摘要和被驱逐消息生成新的递归摘要。被驱逐的原始消息并没有丢失，而是仍保存在 recall storage 中，之后可以通过搜索取回。

##### LLM 通过函数调用管理自己的记忆（这个记忆其实相当于不断更新的摘要）
这里调用的函数应该是预先定义好的，应该只是开了部分的固定的接口，有点像agent中的不同skill

MemGPT 不使用一个完全固定的外部记忆策略，而是让 LLM 自己调用一组记忆函数，例如：

+ 向 working context 写入内容；
+ 修改已有记忆；
+ 搜索 recall storage；
+ 搜索 archival storage；
+ 请求继续执行下一次推理。

所以，记忆编辑和记忆检索都是由模型根据当前上下文自主决定的。模型可以判断某条信息是否重要、是否需要持久化，也可以在回答问题前主动搜索过去的对话或外部文档



+ 比较有意思的点：通过 heartbeat 请求继续推理

普通函数调用可能在执行后暂停，把控制权交还给外部事件或用户。MemGPT 另外设计了函数链机制：LLM 可以在函数调用中请求 `**heartbeat=true**`，表示函数执行完后应该立即再次调用 LLM。

##### 函数链和分页检索支持多跳推理（处理多跳推理）
MemGPT 的函数调用不仅能执行一次搜索，还能连续执行多次调用。例如：

1. 先搜索一个 UUID；
2. 找到它对应的下一个 UUID；
3. 再用新的 UUID 搜索；
4. 重复这一过程，直到找到最终值。

### MemMA：Coordinating the Memory Cycle through Multi-Agent Reasoning and In-Situ Self-Evolution
跳出LLM，上升到对于agent的研究

焦于**长时程对话场景中的 LLM Agent 外部记忆管理问题**：如何让智能体在长期交互中正确地写入、组织、检索和修复记忆，而不是把“记忆构建、记忆检索、答案生成”当成彼此独立的模块。论文将这个问题概括为两个核心困难：前向过程中的“战略盲目”，以及后向过程中的“稀疏且延迟的反馈”。（编码，检索，校正）

+ LLM Agent 的长期记忆；
+ 长时程对话理解；
+ 多智能体协作；
+ 检索增强生成；
+ Agent 的自我反思与自我演化。

三个阶段：（认为整个记忆系统构建，或者）

1. **Construction，记忆构建**：决定什么信息需要保存、更新、合并或删除；
2. **Retrieval，记忆检索**：针对问题从记忆库中找出相关证据；
3. **Utilization，记忆使用**：利用检索到的证据回答问题，并从答案是否正确反过来判断记忆是否有问题。

#### 问题
##### 前向路径中的战略盲目
缺少一个全局规划器来判断：当前应该保存什么、哪里存在冲突、当前检索到底缺少什么信息。

**Myopic Construction，短视式记忆构建**

+ 过度保存低价值细节；
+ 反复追加相似信息；
+ 覆盖互相冲突的事实；
+ 把同一事件拆散成多个不完整的记忆条目。

**Aimless Retrieval，漫无目的的检索**

+ 初始问题表达不准确时，只是机械地改写同义句；
+ 检索到相似但无关的事件；
+ 没有明确判断当前证据到底缺少“日期、人物、地点还是具体事件细节”。

##### 后向路径中的稀疏、延迟反馈
记忆构建时做出的错误决定，可能直到很久以后某个问题回答失败时才暴露出来。例如：

+ 早期对话中没有保存某个专有名词；
+ 把两个相似事件错误合并；
+ 只保存了“去露营”，却没有保存具体看到的是“英仙座流星雨”。

等到后续问题答错时，系统通常只知道“答案错了”，却不知道是哪一条历史记忆导致了错误，因此很难精确修复。

#### 前人工作
##### 改进记忆结构
关注“记忆库应该长什么样”，例如：

+ 按时间顺序保存对话；
+ 使用层次化记忆；
+ 引入图结构或时间知识结构；
+ 将短期记忆与长期记忆分开。

这类方法解决了记忆组织问题，但并不一定能判断某个新信息是否应该保存、应该与哪条记忆合并。

##### 改进记忆写入和组织
代表性系统包括 [Mem0](/abs/2504.19413?chatId=019fd002-f2d0-7e37-86a6-19ff16c5930e)、[A-Mem](/abs/2502.12110?chatId=019fd002-f2d0-7e37-86a6-19ff16c5930e) 和 [LightMem](/abs/2510.18866?chatId=019fd002-f2d0-7e37-86a6-19ff16c5930e)。

它们分别从事实抽取、记忆条目组织、记忆压缩和多阶段记忆结构等角度改进记忆质量。它们通常比简单地保存完整对话更高效，但主要仍然集中于“如何存储和组织”。

##### 改进记忆检索
另一类方法使用：

+ 向量相似度检索；
+ 多轮查询改写；
+ 反思式检索；
+ 基于时间或实体的检索。

它们能够缓解一次检索找不到答案的问题，但如果查询改写没有明确目标，就可能出现论文所说的“检索漂移”：每次只是把问题换一种说法，却没有定位真正缺失的信息。

#### 如何解决问题
可以包裹在不同存储后端之上的多智能体协调框架。（提出一个新的架构，而不是修改模型中的一个部分或者某一个环节）；把“应该做什么”与“具体怎么执行”分开。

1. **Meta-Thinker**：负责高层战略推理；决定目标
2. **Memory Manager**：负责具体记忆编辑；
3. **Query Reasoner**：负责根据缺失信息迭代改写查询；
4. **Answer Agent**：负责最终回答问题。

##### 前向路径：用 Meta-Thinker 协调构建和检索
+ 记忆构建阶段（指导，不具体参与记忆编辑）

当新的对话片段到来时：

    1. Meta-Thinker 查看当前对话和已有记忆；
    2. 判断哪些信息重要；
    3. 标记重复内容和潜在冲突；
    4. 给 Memory Manager 提供结构化指导；
    5. Memory Manager 执行具体操作。
+ 检索阶段

MEMMA 不再只进行一次 top-$k$ 相似度检索，而是采用“判断—改写—再检索”的循环：

    1. Query Reasoner 根据原始问题获取初始证据；
    2. Meta-Thinker 判断证据是否足够回答；
    3. 如果不足，识别最关键的信息缺口；
    4. Query Reasoner 针对这个缺口生成新的查询；
    5. 检索新的证据；
    6. 直到证据足够，或达到检索预算。

这里最关键的不是“多检索几次”，而是明确区分缺失类型。例如：

    - 问题问的是日期，但当前证据只有事件描述；
    - 已经知道某人搬家了，但缺少具体国家名；

##### 后向路径：通过 probe QA 修复记忆（相当于做一个简单测试，验证是否有问题）
每处理完一个会话，系统不会直接把当前记忆提交到长期记忆库，而是先生成一组人工构造的 probe QA：

+ 单跳事实问题；
+ 跨会话推理问题；
+ 时间推理问题。

在实验中，每个会话生成 $J=5$ 个 probe QA。

+ Probe Generation

系统根据当前会话和历史记忆生成问题—答案对。

+ In-situ Verification

系统立即用临时记忆回答这些 probe 问题。如果回答错误，说明当前记忆可能有问题

+ Evidence-Grounded Repair

对于失败的 probe，系统生成一个候选修复事实。例

+ Semantic Consolidation（这个比较关键，是比较特殊的记忆更新约束，之前没有看到过这种约束）

修复事实不能直接全部加入记忆，否则可能重新造成重复和冲突。因此系统在写入之前进行语义整合：

    - **SKIP**：已有记忆已经包含该事实；
    - **MERGE**：同一个事件中存在互补信息，可以合并；
    - **INSERT**：新事实属于不同事件、不同日期或不同主题，应独立插入。

#### 直接修复记忆库，而不只是改进答案
许多反思式 Agent 主要修改：

+ 当前答案；
+ 下一轮提示词；
+ 外部经验总结；
+ 行为策略。

MEMMA 则直接修改主记忆库。它把答案失败转换成记忆修复动作，因此一次失败可能改善之后多个相关问题的回答。

#### 评估指标
+ Token-level F1

衡量生成答案与标准答案在词元层面的重叠程度，偏向词面匹配。

+ BLEU-1

衡量生成答案与参考答案之间的一元词重叠，也属于词面指标。

+ LLM-as-a-Judge Accuracy

由另一个 LLM 判断答案在语义上是否正确，更关注：

    - 是否回答了正确的问题；
    - 是否包含正确的实体；
    - 是否表达了正确的时间；
    - 是否只是措辞不同但语义等价。

因此，F1 和 BLEU-1 主要反映 lexical overlap，而 ACC 主要反映 semantic correctness。

### lightmem（偏效率，轻量化）
聚焦于 **LLM Agent 的长期对话记忆**：在很长、多轮、动态变化的交互中，让模型能够记住、组织和更新历史信息，同时避免记忆系统带来的高 token 消耗、频繁 API 调用和在线延迟。它并不是在改进语言模型本身，而是在解决“模型如何高效地使用外部长期记忆”的问题。

+ 核心思想：**把记忆构建过程拆成三个轻量级阶段，分别对应人类记忆中的感觉记忆、短期记忆和长期记忆。**

#### 解决的问题
外部记忆的写入与组织：冗余，记忆混乱，记忆更新带来延迟与错误

#### 前人工作
##### 原始对话中有大量冗余信息
用户输入和模型回复中，往往包含大量与后续任务无关的内容。传统系统通常直接把这些原始内容交给更强的 LLM 进行摘要或记忆构建，导致：

+ 输入 token 数量很大；
+ 摘要 API 调用次数多；
+ 许多无关内容进入记忆库；
+ 噪声可能反过来干扰模型的上下文理解。

用于记忆存储的模型也得考虑效率（之前都是默认将所有的记忆投入，例如memMA，就是将当前的输入与bank中的记忆都作为输入？）

之前的系统往往是在“先完整处理，再尝试压缩”，而不是在进入昂贵的记忆构建流程之前就过滤冗余信息。

##### 固定粒度切分容易造成主题混杂
许多方法以单轮对话或固定长度窗口作为记忆构建单元。如果一个固定窗口中包含多个不同主题，LLM 在摘要时就可能把多个主题混在一起，导致：

+ 记忆条目不准确；
+ 重要细节丢失；
+ 后续检索时难以精确定位；
+ 每一轮都单独构建记忆，效率又比较低。

##### 在线更新记忆带来延迟和错误覆盖
传统记忆系统经常在用户交互的实时过程中执行更新、冲突检测、删除和合并。这会带来两个问题：

+ 更新操作需要调用 LLM，增加在线响应延迟；
+ LLM 可能错误地把“新增信息”判断为“旧信息冲突”，从而删除仍然有用的历史内容。

#### 如何解决问题
##### 感觉记忆——先压缩，再进行主题切分
1. 预压缩：首先使用轻量的 [LLMLingua-2](https://www.alphaxiv.org/abs/2403.12968?chatId=019fd0ac-01c9-7a06-8ada-7aaf19eadf76) 对原始输入进行 token 级别的筛选，只保留更有信息量的 token。论文的默认实现中，LLMLingua-2 负责判断每个 token 是否应该保留，而不是让主 LLM 直接处理完整原文。
2. 主题切分：与原子技能分割有点类似，需要寻找边界信息

压缩后的内容会先进入一个 sensory memory buffer。当 buffer 达到容量后，LightMem 使用两种信号判断主题边界：

    - **注意力信号**：寻找相邻句子注意力变化中的局部峰值；
    - **语义相似度信号**：如果相邻句子的 embedding 相似度较低，说明可能发生了主题转换。（这个和思源的想法比较接近）

##### 主题感知的短期记忆
Q：不再是一输入一回答？应该是一个session被分为多个part，然后对一部分part进行摘要后回答？

A：这个地方为什么是短期记忆，因为相当于接近直接存储，当buffer达到上限之后，会调用LLM来生成摘要，融合到长期记忆中； 记忆存储与回答是两条线，回答是一直在进行的；这篇文章提出的就是聚焦于外部记忆库的优化为主

完成主题切分之后，LightMem 会把相关的对话轮次组织成：

```plain
$$ 
\{\text{topic}, \text{message turns}\}
$$
```

这些主题片段先进入 STM buffer。只有当 STM buffer 达到设定阈值时，系统才调用主 LLM，对每个主题片段生成摘要。

最终存储的记忆条目大致包含：

```plain
$$ 
\{\text{topic},\text{summary embedding},\text{user turns},\text{model turns}\}
$$
```

相比“每一轮对话调用一次摘要模型”，这种做法有两个好处：

1. 多个相关轮次可以一起摘要，减少 API 调用；
2. 不同主题不会被强行放进同一个摘要中，降低语义混杂。

因此，Light2 实际上是在效率和摘要质量之间寻找一个更好的粒度：不是细到每一轮，也不是粗到整个 session，而是以主题为单位进行批量处理。

##### 长期记忆——在线软更新，离线休眠更新
##### 在线阶段：只做 soft update
新的记忆条目产生时，LightMem 不在实时交互过程中进行复杂的删除、合并和冲突判断，而是先把条目直接插入长期记忆库，并记录时间戳。在线阶段优先保证信息不丢失，而不是立即决定哪些旧信息应该被删除。

##### 离线阶段：sleep-time update
在后台或预设的“休眠时间”中，LightMem 才执行更复杂的记忆维护：

1. 为每个记忆条目寻找语义相近的候选条目；
2. 只允许时间更晚的条目去更新更早的条目；
3. 为每个条目建立独立的 update queue；
4. 对不同队列中的更新操作进行并行执行。

### ENGRAM
研究的是**大语言模型对话代理的长期记忆问题**：当用户与助手进行跨多轮、跨会话的长期交流时，系统如何记住过去发生的事件、用户的稳定偏好和操作流程，同时避免上下文过长带来的成本、延迟和“记不住重点”等问题。文章提出的 ENGRAM 采用三类记忆和简单的向量检索；

#### 解决的问题

#### 前人工作
1. **非参数化检索方法**。系统把过去对话保存在一个外部存储中，回答问题时通过稠密向量检索或词法检索找回相关片段。这类方法结构相对直接，也容易更新，但效果依赖文本切分方式、embedding 质量和检索器校准。

### GAM: Hierarchical Graph-based Agentic Memory for LLM Agents
研究的是**大语言模型（LLM）智能体的长期记忆**

+ LLM Agent；
+ 长期对话记忆；
+ Agentic Memory；
+ 图结构记忆；
+ 检索增强生成。

核心思想：**把实时记忆编码和长期记忆整合分开处理。 lightmem？**

#### 解决的问题
智能体怎样在长期、多轮、不断变化的对话中，既快速吸收新信息，又避免短期噪声破坏已经形成的稳定知识，并且能够准确地找回相关上下文。

长期记忆系统同时需要满足两个看似矛盾的目标：

1. **快速写入新信息**：新对话不能等很久才能被记录；
2. **稳定保存旧知识**：临时、错误或无关的信息不能污染长期记忆。
+ **Memory Contamination**：新信息或噪声直接写入长期记忆；（记忆的更新规则）
+ **Memory Loss**：持续更新导致旧节点逐渐失去连接，最终难以被找回；
+ **Semantic Drift**：不同主题被错误合并，使智能体对用户或事件形成错误理解。（类似于原子技能合并，prototype的更新规则）

#### 前人工作
##### 统一流式记忆：持续追加或更新
第一类方法把对话维护成一个连续的信息流。新内容通常直接追加到记忆流，或者与已有记忆进行合并。

它的优点是：

+ 更新速度快；
+ 适合实时对话；
+ 不需要复杂的结构化处理。

但问题是缺乏**写入隔离**。新信息、旧信息和临时噪声都进入同一个存储空间，因此会产生记忆污染、语义漂移和旧信息遗忘。

##### 离散结构化记忆：知识图谱或固定结构
使用知识图谱、实体节点或预定义的结构组织记忆。（ENGRAM就是这个问题，预定义的结构潜在就是有人为先验介入，而且比较硬性）

它们的优点是：

+ 长期知识更稳定；
+ 适合实体关系和多跳推理；
+ 检索路径更清晰。

但代价是结构通常比较刚性：

+ 需要较昂贵的索引构建；
+ 难以适应对话主题的连续变化；
+ 容易把自然对话切割成碎片；
+ 对用户状态、话题演化和子主题变化的表达不够灵活。

##### 动态结构或检索优化方法
还有一些工作尝试让记忆结构动态变化，或者重点优化检索过程。但论文认为，这些方法经常依赖：

+ 固定 token 数；
+ 固定轮数；
+ 人为规定的状态切换；
+ 只改善检索，而不改变记忆的写入和整合机制。

也就是说，它们可能改善“从记忆中找什么”，但没有彻底解决“什么时候应该把信息写入长期记忆，以及如何避免写入污染”的问题。

#### 如何解决问题
+ 整体记忆结构
    - G_event：当前对话的事件进展图；
    - $G_{\text{topic}}$：长期主题关联网络；
    - $S_{\text{arch}}$：已经整合过的历史事件图归档；
    - $E_{\text{cross}}$：连接主题节点和原始事件证据的跨层链接。

##### 阶段一：Episodic Buffering，事件缓冲
新到来的每句话首先被表示为一个事件节点，并追加到当前的 **Event Progression Graph** 中。

这个局部图主要记录：

+ 对话发生的顺序；
+ 事件之间的时间关系；
+ 事件之间的因果或上下文联系；
+ 当前主题中的细节。

重要的是，这些内容暂时只写入局部图，不直接修改长期主题网络。

##### 阶段二：Semantic Consolidation，语义整合
当系统判断当前话题已经发生了语义切换，或者当前缓冲区达到上限时，GAM 才会把局部事件整合到长期记忆中。

论文的实现有几个关键点：

+ 维护一个最多约 2048 token 的事件缓冲区；
+ 不在每一轮对话后都调用边界检测器；
+ 在会话结束、自然停顿或缓冲区溢出等稀疏维护时机进行检查；
+ 使用 LLM 判断对话中是否出现了真正的主题边界。

那么这两个阶段和light mem，先存储，达到上限后总结归入长期记忆是类似的

##### 阶段三：双粒度保存
当一个事件图被整合时，生成一个新的语义节点：和崇神的文章类似

+ $c_{\text{sum}}$ 是高层摘要，用于主题理解和语义检索；
+ $c_{\text{raw}}$ 是原始对话内容，用于保留细节。

只保存摘要可能导致姓名、时间、原话等细节丢失；只保存原文又会导致长期检索成本过高。随后，系统先用向量检索找到最相近的少量主题节点，再用 LLM 判断它们之间的关系和置信度，而不是让新节点与全图中的所有节点进行昂贵比较。整合完成后，原始事件图被归档，并通过跨层边与新主题节点连接。

##### 阶段四：图引导的多因素检索（分层检索）
查询时，GAM 不直接对所有原始记忆做一次平面向量检索，而是采用“从主题到细节”的层级检索：

1. 在主题关联网络中找到与问题最相关的主题节点；
2. 扩展到这些主题的一阶邻居，补充潜在相关主题；
3. 沿着跨层链接找到对应的历史事件图；
4. 取得具体事件和原始对话细节；
5. 使用多因素重新排序。

除了语义相关性外，还会考虑：

+ **时间因素**：问题是否要求特定时间；
+ **置信度因素**：该记忆是否通过了编码阶段的一致性检查；
+ **角色因素**：记忆中的说话者或人物是否与问题相关。

### Hindsight（个人认为这篇文章比较臃肿）
面向长期运行的 LLM Agent 记忆架构；**LLM Agent Memory，也就是大语言模型智能体长期记忆** 领域，重点是长期、多轮、多会话对话中的记忆管理。

#### 解决的问题
+ 解决智能体在跨会话交互中“记不住、找不到、分不清事实与信念、难以保持稳定偏好”的问题。

传统 Agent Memory 通常采用以下流程：

1. 从历史对话中抽取一些重要片段；
2. 存入向量数据库、关键词索引或知识图谱；
3. 用户提问时检索 top-$k$ 条记忆；
4. 把检索结果拼接到 Prompt 中，让一个基本无状态的模型生成答案。
+ **长期信息保存不完整**：跨很多会话后，重要信息可能被遗漏；
+ **检索只关注相似度**：相关信息可能通过时间、实体或因果关系连接，而不是通过词面相似度连接；（相似度仅为表象，缺乏因果关系）
+ **事实、经历、总结和主观信念混在一起**：模型无法清楚地区分“我观察到的事实”和“我形成的观点”；
+ **缺乏稳定的行为和偏好**：同一个 Agent 在不同对话中可能给出局部合理、但彼此矛盾的回答。（需要长期的一个用户画像？）

另一类方法把历史信息组织成知识图谱，使用实体、关系和时间信息进行检索。这比单纯的向量检索更适合回答“某件事什么时候发生”“某个人与哪些事件有关”等问题。

+ 记忆缺乏主题分类，同时更新机制需要优化

##### 强化学习、持续学习和参数化记忆
还有一些工作尝试通过强化学习优化记忆操作，或者把记忆写入模型参数、进行持续学习。这些方法有可能提高长期适应能力，但参数化记忆通常更难编辑、追踪和解释；强化学习记忆系统也通常关注任务准确率，而不是事实、观点和行为风格之间的结构化关系。

:::info
##### 已有系统普遍缺少以下组合能力：事实和意见分离、意见随证据演化、行为参数、置信度、多策略检索以及完整的外部记忆结构。
事实是客观，意见是主观；主观意见需要更新，根据事实纠正，更新；更合理，优秀的外部记忆结构

:::

#### 如何解决问题
+ **核心思想：不要把 Agent Memory 只看成一个供 RAG 使用的文本数据库，而要把它作为 Agent 推理的基础设施。**

它由两个主要组件组成：

+ **TEMPR**：负责 `retain` 和 `recall，即记忆写入与记忆召回；
+ **CARA**：负责 `reflect，即基于记忆进行带有偏好和信念更新的反思。

:::info
构建闭环，不能仅是前向开环，需要闭环反馈

:::

##### 四种记忆网络
| **网络** | **保存内容** | **作用** |
| :--- | :--- | :--- |
| World | 关于外部世界的客观事实 | 例如“某人在某公司工作” |
| Experience | Agent 自己经历过的事情、行动和建议 | 例如“我曾经向某人推荐某个地点” |
| Opinion | Agent 的主观观点、判断和置信度 | 例如“我认为某种方案更适合某类任务” |
| Observation | 从多个事实中总结出的、尽量客观的实体画像 | 例如“某人是一名专注机器学习的软件工程师” |


+ “Agent 自己做过什么”；
+ “Agent 如何评价这件事”； 

opinion：可以认为是记忆更新机制，区别直接粗暴更新记忆，作为独立的模块来区分

##### Retain：以叙事事实而不是碎片保存记忆（编码）
倾向于将这些内容合并成一个保留参与者、动机、讨论过程和最终决定的叙事事实。这样做可以减少碎片化，也能保留跨句子的因果关系和决策过程。

每条事实还会附带：

+ 起止时间和提及时间；
+ 参与者和实体；
+ 事实类型；
+ 向量表示；
+ 与其他事实的关系。

系统会构建四种图连接：

1. **实体连接**：提到同一个人、组织或地点的记忆相互连接；
2. **时间连接**：时间上相近的事件相互连接；
3. **语义连接**：向量表示相似的事实相互连接；
4. **因果连接**：一个事实导致、促成或阻止另一个事实。

##### Recall：四路检索并融合
+ **语义检索**：寻找含义相近的记忆；
+ **BM25 关键词检索**：适合专有名词、API 名称和数据集名称；
+ **图扩散检索**：沿着实体、时间和因果边寻找多跳相关信息；
+ **时间检索**：先解析问题中的时间范围，再筛选真正发生在该时间段内的事实。

四路结果之后使用 Reciprocal Rank Fusion（这个是使用每个检索列表中的排名，而不直接比较原始分数。因为量纲不一样），也就是基于排名的融合方法，再通过 cross-encoder 进行神经重排序，最后根据 token budget 选择能够放入下游模型上下文的记忆。

+ 这里比较特殊的是一个token budget ，约束检索出的上下文长度或者topk数量，实现动态调节（但是这个效果是附带的，因为没有明确去指定自适应topk选择）

##### Reflect：让 Agent 基于记忆形成并更新观点
CARA 在召回到事实之后，不只是生成一个答案，还会利用 Agent 的行为画像来影响推理风格。

行为画像包括：

+ **Skepticism**：怀疑程度；
+ **Literalism**：对字面含义的依赖程度；
+ **Empathy**：对情绪和人际影响的重视程度；
+ **Bias strength**：这些偏好影响回答的强度。

例如，同一组关于远程工作的事实：

+ 低怀疑、高同理心的 Agent 可能强调灵活性、自主性和创造力；
+ 高怀疑、强字面理解、低同理心的 Agent 可能强调结构、监督和问责。

这些参数不是简单地改变 Prompt 语气，而是用于影响 Agent 如何形成主观意见。

Opinion 网络中的观点不是静态标签。新事实到来时，系统会判断它们对已有观点是：

+ reinforce：支持；
+ weaken：削弱；
+ contradict：矛盾；
+ neutral：无关。

随后更新观点的置信度；支持证据提高置信度，削弱证据降低置信度，强矛盾证据会更大幅度降低置信度，必要时还会重写观点文本。

（为什么图片中会有agent的回答用来更新observation？这个不应该使用客观事实进行更新吗？）

###### 这个机制的局限
论文中的更新仍然比较粗糙：

1. $\alpha$ 是固定步长；
2. 没有显式区分证据强弱；
3. 没有根据证据来源可靠性加权；
4. 没有处理多个相互独立证据之间的相关性；
5. `reinforce` 和 `contradict` 主要依赖 LLM 判断；
6. 观点初始值本身可能已经受到 Agent disposition 的影响。

### MEM: Multi-Scale Embodied Memory for Vision Language Action Models（机器人）
聚焦于机器人学习中的视觉—语言—动作模型（VLA）如何利用多时间尺度记忆完成长时程、部分可观测的操作任务。核心结论是：机器人不能只依赖当前画面，也不能简单地把所有历史画面都塞进模型；它需要同时具备“最近几秒的视觉记忆”和“持续十几分钟的语义记忆”。

#### 解决的问题
传统 VLA 根据当前相机观测和语言指令直接预测机器人动作。这种方式在短任务上有效，但遇到以下场景就会失败：

+ 任务持续十几分钟，需要记住哪些步骤已经完成；
+ 物体被机械臂挡住，机器人需要记住物体刚才在哪里；（对应LLM中信息缺失时回忆？）
+ 机器人刚才尝试了一种失败的抓取方式，之后应该换一种策略；（对于错误回答的标记）
+ 任务中包含计数、等待、顺序约束，例如“已经放入两个咖啡勺，再放一个就错了”。

**如何让机器人以较低的推理延迟，同时记住近期的精细视觉信息和远期的抽象任务状态。（近期需要精细，记忆可以较抽象，LLM或agent响应也需要时效性）**

#### 前人工作
##### 循环记忆模块
较早的方法使用 RNN 或其他 recurrent memory，把历史状态压缩到一个隐藏向量中。优点是计算开销较低，但记忆内容通常比较隐式，难以保证模型保留了任务中真正重要的信息。

##### 直接输入历史观测
更近期的 Transformer 类方法会把多帧历史图像、状态或动作直接作为上下文输入。这样能够保留较多细节，但随着时间跨度增加，计算量和推理延迟会迅速增长，难以支持长达数分钟的任务。

##### 对历史观测进行压缩
其他方法尝试只保留：

+ 机器人自身的本体状态；
+ 2D 点轨迹；
+ 少量关键帧；
+ 一个池化后的 memory token；
+ 自然语言形式的历史摘要。

这些方案各有局限。**只保留本体状态无法记住环境中的抽屉、物体和空间布局；平均池化会损失关键的时序信息；关键帧过于稀疏时可能丢失动作动态；只使用自然语言又难以表达精细的抓取角度、物体位置和遮挡关系。**论文指出，**不存在一种单一模态能够同时满足短期精细控制和长期语义记忆的需求**。

#### 如何解决问题
MEM 把机器人策略分成高层和低层两个部分

##### 长期记忆：用语言记录语义事件
训练时，作者把机器人轨迹中的子任务指令以及每个子任务成功或失败的信息交给预训练语言模型，让语言模型生成应该保留的摘要。

关键点是：**语言记忆不是简单追加历史指令，而是主动压缩和删除无用信息**。例如，机器人不必永久记住每个碗的颜色，只需记住“已经把三个碗放进右上方柜子”。这样可以降低记忆长度，也能减少训练和推理之间的数据分布差异。

:::info
这里存储的是类似于长期的agent的主观记忆

:::

##### 短期记忆：用视频编码器保留近期视觉细节
短期记忆需要回答更精细的问题，例如：

+ 机械臂刚才从哪个方向抓取？
+ 物体是否已经滑动？
+ 门刚才朝哪个方向被尝试打开？
+ 机器人擦拭表面已经进行了多久？

为此，MEM 将普通的图像 Vision Transformer 改造成视频编码器：

1. 每一帧图像先独立切分为 patch；
2. 大多数层执行空间注意力；
3. 每隔若干层加入沿时间维度的因果注意力；
4. 最后只把当前时刻的 token 送入 VLA 主干网络，但这些 token 已经融合了过去帧的信息。

这样，历史帧的信息被压缩到当前帧的表示中，而不需要把所有历史帧的 token 都继续传给后续模型。（LLM中短期记忆是不是还是提供的还是原始的对话信息），它使用空间—时间分离的注意力

A key property of our video encoder is that it does not introduce new learnable parameters compared to standard, single-image ViTs.

没有引入新的需要训练的参数，直接根据特性进行修改结果与运算，修改ViT的注意力模式就可以实现，但是需要添加时序的位置编码，因为有时序注意力计算

##### **记忆能够支持“上下文内策略适应”。**
机器人可以根据近期失败记忆改变行为，而不必依赖显式的任务重规划。例如，第一次抓筷子失败后调整抓取高度，或者第一次向错误方向拉冰箱门失败后尝试另一方向。

### ReACT
大语言模型在生成**语言推理轨迹（Thought）的同时生成环境动作（Action）**，并通过环境返回的观察结果（Observation）不断修正计划，从而统一处理“推理”和“行动”两类任务。

两个研究方向的交叉处：

1. **大语言模型的复杂推理**，例如多跳问答和事实核验；
2. **语言模型驱动的交互式决策或智能体**，例如在文本环境中寻找物品、浏览网页和执行任务。

#### 解决的问题
此前的工作通常把“推理”和“行动”分开处理，但真实任务往往要求两者循环配合。

#### 前人工作：
##### 只做推理：Chain-of-Thought
[Chain-of-Thought（CoT）](/abs/2201.11903?chatId=019feef2-ac35-7e4e-bafd-cc2fcaae84ea) 通过在最终答案前生成中间推理步骤，让模型把复杂问题拆解成多个步骤。

它的优点是：

+ 能显式分解问题；
+ 能进行多步逻辑推理；
+ 不需要额外的环境或工具。

但它的问题是推理过程基本停留在模型内部：

+ 模型无法通过搜索或环境交互核实事实；
+ 如果某一步产生错误事实，后续推理可能继续建立在错误之上；
+ 对动态环境和长序列行动支持较弱。

##### 只做行动：Action-only 或语言模型策略
另一类方法让语言模型直接根据观察结果生成动作。例如在文本游戏或网页环境中，模型可以输出：

text

```plain
go to cabinet 1
take knife 1
```

这类方法能够与环境交互，但通常缺少显式的高层推理：

+ 不容易把复杂目标分解成子目标；
+ 不容易跟踪已经完成了哪些步骤；
+ 出错后容易重复生成无效动作；
+ 无法充分利用常识来决定下一步应该搜索哪里。

##### 浏览和规划相关方法
[WebGPT](/abs/2112.09332?chatId=019feef2-ac35-7e4e-bafd-cc2fcaae84ea) 让语言模型浏览网页并回答问题，但论文认为它没有显式建模可检查的思考过程，而是更多依赖训练和人类反馈。

在机器人规划方面，[SayCan](/abs/2204.01691?chatId=019feef2-ac35-7e4e-bafd-cc2fcaae84ea) 让语言模型提出候选动作，再由 affordance 模型根据实际环境对动作进行筛选；[Inner Monologue](/abs/2207.05608?chatId=019feef2-ac35-7e4e-bafd-cc2fcaae84ea) 则加入了来自环境的反馈。不过，论文认为 Inner Monologue 中的“inner monologue”主要是对环境状态和完成情况的反馈，缺少 ReAct 那样灵活的高层目标分解、常识推理和计划调整。

#### 如何解决问题
##### 把“语言思考”也纳入动作空间
ReAct 的关键形式化非常简单。传统智能体的动作空间是 $A$，只能生成环境动作；ReAct 将它扩展为：

$$   
\hat{A}=A\cup L  
$$

Thought 不会直接改变环境，因此不会产生新的环境观察；它的作用是把有用的信息加入上下文，帮助下一步推理或行动。

##### 根据任务类型调整思考密度
ReAct 并不是每一步都强制生成长篇思考，而是根据任务类型采用不同策略：

+ 对 HotpotQA 和 FEVER 这类知识密集型任务，采用较密集的 Thought–Action–Observation 交替；
+ 对 ALFWorld 和 WebShop 这类长时序决策任务，只在目标分解、子目标完成、计划改变等关键位置生成较稀疏的 Thought，让模型自己决定何时思考。

这种设计避免了两个问题：

+ 思考太少：模型无法规划和跟踪状态；
+ 思考太多：长任务中上下文迅速膨胀，行动效率下降。

论文还强调，ReAct 不需要设计新的模型结构或复杂的专用推理模块，而是冻结大型语言模型，通过少量人工编写的 Thought–Action 轨迹进行 few-shot prompting。

##### 创新一：统一推理和行动
它不是单纯改进 CoT，也不是单纯让模型调用工具，而是把两者放进同一个连续轨迹中：

$$   
\text{Thought}\rightarrow \text{Action}\rightarrow \text{Observation}\rightarrow \text{Thought}  
$$

这使得模型可以一边思考，一边从外部世界获得新信息。

##### 创新二：建立闭环，而不是一次性生成计划
传统规划常常先生成完整计划，再执行；如果环境和预期不一致，计划就可能失效。

ReAct 的计划是动态的。每次观察结果都会进入上下文，模型可以：

+ 更新对环境的认识；
+ 改变搜索关键词；
+ 跳过已经完成的子目标；
+ 处理异常；
+ 从失败动作中恢复。

当思考和observation的反馈不一致时，重新规划

##### 创新三：用语言作为工作记忆
Thought 不仅是解释，也承担了工作记忆的功能。

##### 创新四：同时提升事实性、可解释性和可控性
对于知识任务，环境查询能够减少凭空生成事实；对于交互任务，显式 Thought 能帮助人理解模型为什么选择某个动作。

论文还展示了人类可以直接修改某一步 Thought，从而改变模型后续行为。例如删除一个错误的想法，再加入关于物品可能位置的提示，模型就能够从失败轨迹转向成功轨迹。

### EverMemOS（记忆构建，编码）
**大语言模型智能体的长期记忆**，更具体地说，是“面向长期交互的 LLM Memory Operating System”。

#### 解决的问题
普通聊天模型主要依赖当前上下文窗口，但真实的个人助理、客服、医疗咨询或办公智能体需要记住用户数天、数月甚至数年的经历，并在新问题中正确使用这些信息。问题并不只是“能不能找到旧信息”，而是：

如何把长期对话中分散、重复、相互更新甚至相互冲突的信息，组织成稳定、具有时间意识、能够支持长期推理的记忆？

试图解决的正是这种 **跨时间整合经验、解决冲突和维持一致用户状态** 的问题。

#### 前人工作
##### 直接扩展上下文窗口
最直接的方法是把更多历史对话放进上下文，或者使用更长上下文模型。这样不需要设计额外的记忆系统，但有三个问题：

1. 历史越长，计算成本越高；
2. 模型不一定能有效利用长上下文；
3. 信息虽然都在上下文中，但模型仍然可能无法识别哪些内容已经过时、哪些内容更重要。

##### 检索式记忆或 RAG
另一条路线是把历史对话切成文档、事实或片段，然后根据当前问题检索相关内容。这种方法降低了上下文长度，但通常把记忆看成一个“平坦的记录集合”，（统一对待，无取舍，无整合）

它擅长找出局部相关内容，但不一定能把多个时间点的证据整合起来。例如，用户的偏好变化、健康状态变化和旅行经历可能分散在多个对话中，单独检索其中一条记录无法得到完整结论。（具有局限性，不是全局视角）

##### 参数化记忆或可训练记忆（训练涉及灾难性遗忘）
还有一些工作尝试把用户信息写入模型参数，或者训练专门的记忆模块。这样可以减少外部检索，但容易产生遗忘、更新不稳定和难以审计等问题。

##### 已有的 Memory OS 和结构化记忆
近年来出现了 [Mem0](/abs/2504.19413?chatId=019fef06-f416-7396-ab9d-c560b1718d6f)、[Zep](/abs/2501.13956?chatId=019fef06-f416-7396-ab9d-c560b1718d6f)、[MemOS](/abs/2507.03724?chatId=019fef06-f416-7396-ab9d-c560b1718d6f)、[MemoryOS](/abs/2506.06326?chatId=019fef06-f416-7396-ab9d-c560b1718d6f) 等系统，它们进一步引入事实维护、层次化存储、知识图谱或统一记忆调度。

EverMemOS 认为，这些方法虽然已经超越了简单的文本存储，但许多系统的主要重点仍然是：

+ 如何存储记忆；
+ 如何压缩记忆；
+ 如何维护事实；
+ 如何快速检索。

而本文强调的缺口是：**如何把经历组织成不断演化的高层语义结构，并在推理时主动重构出足够但不过量的上下文。**

#### 如何解决问题
##### 阶段一：Episodic Trace Formation
系统首先把连续对话切分成相对完整的事件或主题片段。这个阶段包括：

1. **语义分段**：检测话题是否发生变化；
2. **叙事合成**：将多轮、冗余、带有代词和省略的对话，改写成简洁的第三人称事件叙述；
3. **结构化推导**：从事件中提取原子事实和未来相关信息。

最终形成的基本单位叫 **MemCell**。它包含四部分：

+ **Episode**：对发生过的事件进行概括；
+ **Atomic Facts**：可精确检索的原子事实；
+ **Foresight**：面向未来的推断，例如计划、临时状态和近期需要做的事情；
+ **Metadata**：时间戳和来源等元数据。

##### 阶段二：Semantic Consolidation
随后，EverMemOS 不会让所有 MemCell 永远平铺在数据库中，而是进行在线语义聚类：

+ 新 MemCell 到来后，计算它与已有 MemScene 的相似度；
+ 如果相似度超过阈值，就将它合并进已有场景；
+ 否则就创建新的 MemScene；
+ 场景摘要会随着新证据不断更新。

例如，关于“旅行计划”的多个 MemCell 可以被归入同一个 MemScene；关于“健康管理”的不同日期记录也可以组织到同一主题下。

与此同时，系统还会从场景摘要中更新用户画像，区分：

+ 稳定的显式事实；
+ 随时间变化的事实；
+ 用户的隐含特征、偏好和习惯；
+ 新旧信息之间的冲突。

##### 阶段三：Reconstructive Recollection
查询到来时，EverMemOS 不是简单地取出若干最相似文本，而是进行“重构式回忆”。

它大致经过以下步骤：

1. 使用原子事实进行混合检索；
2. 将 dense retrieval 和 BM25 通过 Reciprocal Rank Fusion 合并；
3. 根据 MemCell 的相关性给 MemScene 打分；
4. 选择最相关的若干 MemScene；
5. 从这些场景中重新排序 Episode；
6. 过滤掉已经过期的 Foresight；
7. 用一个 LLM 检查当前上下文是否足以回答问题；
8. 如果不足，则重写查询并进行第二轮检索。

##### 创新一：从“存储记录”转向“组织经验”
传统记忆系统更像数据库：保存若干事实或对话片段，然后按照查询取回。EverMemOS 则试图模拟一个计算意义上的记忆过程：

text

```plain
原始经历 → 情节记忆 → 语义场景 → 用户画像 → 面向查询的重构
```

##### 创新二：同时保留 Episode、Fact 和 Foresight
许多系统只保存事实，但事实并不总能表达事件的上下文和未来有效期。

EverMemOS 同时保存：

+ 发生了什么；
+ 可以精确验证的事实是什么；
+ 这个状态或计划在什么时候有效。

这使它能够区分“用户永久喜欢素食”和“用户这两周正在进行低糖饮食”，也能够过滤已经过期的计划或临时状态。

##### 创新三：场景驱动的检索，而不是片段驱动的检索
系统首先选取相关 MemScene，再从场景内部选择具体 Episode。这种两层结构有助于把分散在不同轮次中的证据放到同一个语义上下文中，特别适合多跳问题、时间问题和知识更新问题。

##### 创新四：把检索变成带验证的主动过程
许多 RAG 系统只进行一次检索。EverMemOS 增加了“充分性检查”：

+ 当前证据是否真的覆盖问题？
+ 是否缺少某个实体、时间或属性？
+ 如果缺少，应该如何改写查询？

这使检索器不仅负责“找相似内容”，还负责发现自己当前找得不够。

##### 创新五：把用户画像纳入记忆生命周期
用户画像不是一个独立的静态模块，而是由 MemScene 的累积摘要不断更新。PersonaMem-v2 实验显示，加入画像后，整体准确率为 53.25%，而只使用 Episode 时为 43.93%，提升 9.32 个百分点。

### Memori（轻量化）
在编码上做的更好，更高效

聚焦于 **LLM Agent 的长期持久记忆（persistent memory）**，核心问题是：如何让智能体在跨会话、跨模型交互中记住用户信息，同时避免把越来越长的历史对话全部塞进上下文，从而造成高成本、检索噪声和“context rot（上下文腐化）”。

#### 解决的问题
普通 LLM 在一次对话中可以利用上下文，但在新的会话中通常无法自动记住此前发生的事情。因此，Agent 需要一个位于应用和 LLM 之间的外部记忆层，用来保存用户偏好、历史事实、任务进展以及时间变化。

文章认为，真正的困难不只是“把历史对话存下来”，而是把噪声很大的对话转换成一种**容易检索、占用 token 少、又能支持后续推理的结构化表示**。Problem Framing

具体来说，系统需要同时解决四个问题：

1. **长期保存**：信息要跨越多轮、多个 session 保留下来。
2. **准确检索**：用户问到某个事实时，能找到真正相关的信息。
3. **时间推理**：能够区分“过去喜欢什么”和“现在喜欢什么”。
4. **成本控制**：不能每次都把几万 token 的完整历史传入模型。

#### 前人工作
+ 直接使用完整上下文
+ 使用传统 RAG
+ 使用专门的记忆系统

这些系统已经尝试解决长期记忆、信息提取和检索问题，但本文认为，仍然存在一个核心权衡：

    - 保留更多原始上下文，通常有利于复杂推理，但 token 成本更高；
    - 压缩得更厉害，成本更低，但可能丢失时间关系、背景和细节。

因此，本文的基本出发点是：**记忆系统的关键不是存储更多文本，而是构造更好的记忆表示。**

#### 如何解决问题
##### 先把对话转换成语义三元组（主谓宾结构）
Memori 不直接保存和检索完整句子，而是从对话中提取原子级事实，形成：

$$   
(\text{subject},\ \text{predicate},\ \text{object})  
$$

例如，一段对话可能被转换为：

+ 用户 —— 喜欢 —— 徒步旅行
+ 用户 —— 工作地点 —— 旧金山
+ 用户 —— 计划 —— 明年去日本

这些三元组重点保存：

+ 用户事实；
+ 用户偏好；
+ 任务约束；
+ 随时间变化的属性。

##### 同时生成会话摘要
仅有三元组也不够，因为三元组会丢失叙事和背景

这个事实并不能说明用户为什么喜欢它，也不能说明这个偏好是否后来发生了变化。

因此，Memori 对**每个会话线程同时生成摘要**，摘要包含：

+ 用户的整体意图；
+ 对话的时间顺序；
+ 任务如何发展；
+ 某个决定背后的隐含上下文。

三元组与对应的会话摘要相互关联：三元组负责精准事实，摘要负责背景和连续性。

##### 使用混合检索
实验中，三元组经过 embedding 后存入本地向量索引，并结合：

+ embedding cosine similarity；
+ BM25 关键词匹配。

这样做的目的，是同时利用语义相似度和精确词匹配，降低单纯向量检索可能出现的偏差。最终检索到的三元组及其对应摘要会一起提供给回答模型。

##### 保持 LLM 侧的解耦
Memori 位于应用和模型之间，不绑定某一个模型供应商。理论上，底层模型可以替换，而持久化的记忆仍然可以复用。这使它更像一个独立的 Agent memory infrastructure，而不是某个模型内部的专用组件。

### ByteRover: Agent-Native Memory Through LLM-Curated Hierarchical Contex
智能体长期记忆（agentic memory / Memory-Augmented Generation, MAG）**中的一个核心问题：如何让智能体在长期、多轮、跨会话任务中，可靠地保存、组织、检索和更新知识，而不是每次都<font style="background-color:#FBDE28;">依赖一个与智能体“割裂”的外部记忆服务。</font>

#### 解决的问题
大多数记忆方法：智能体负责“理解”知识，但另一个外部管线负责“存储”知识。

（认为是比较独立的，僵硬的系统吧），然后现在的记忆系统中都是结果，即最终压缩后的记忆，但是没有为什么这么压缩的证据链，与思维链。

这种架构会带来三个主要问题：

1. **语义漂移**：智能体想保存一个带有背景、原因和条件的复杂结论，但外部服务可能只是机械地切块或生成向量，导致实际保存的内容与原意不一致。
2. **协作上下文丢失**：多个智能体可以共享数据，却不一定共享“为什么得到这个结论”“接下来应该做什么”等推理背景。
3. **故障恢复脆弱**：智能体崩溃后，需要重新查询记忆服务，再从返回的片段中推断任务进展，恢复过程容易出错。

#### 前人工作
已有的长期记忆方法大致分为四类：

+ **轻量级语义记忆**：把文本片段嵌入向量空间，通过相似度检索；
+ **实体中心或个性化记忆**：围绕人物、对象或实体保存属性和值；
+ **情景式和反思式记忆**：将交互组织成事件、情景或更高层次的总结；
+ **结构化和层级式记忆**：利用知识图谱、层级目录或不同记忆层级组织信息。

大多仍然采用类似的交互方式：

1. 智能体把内容序列化；
2. 发送给外部记忆服务；
3. 外部服务自行进行切分、嵌入、实体抽取或图构建；
4. 智能体未来再通过 API 查询；
5. 返回的结果重新注入提示词。

**知识的组织方式不是由正在执行任务的智能体决定的，而是由外部存储管线决定的**。嵌入模型偏向表面相似性，实体抽取管线也有自己的“重要性判断”，而智能体通常看不到记忆是如何组织的，也不知道某条关系为什么被创建。

但它们的缺点是：

+ 结构可能与任务语义不匹配；
+ 难以保存推理过程和行动意图；
+ 检索结果可能只是“相似”，但不一定是“相关”；
+ 对智能体任务状态和故障恢复的支持不足

相当于将planner与memory进行解耦，但是实际上要耦合在一起

#### 解决问题的方法
ByteRover 的核心思路是**反转传统记忆架构**：

<font style="background-color:#FBDE28;">不是让智能体调用一个独立的记忆服务，而是让负责推理的同一个 LLM 直接负责记忆的整理、结构化和查询。</font>

文章把记忆操作定义成智能体工具的一部分。智能体不仅可以调用文件读写、代码执行等工具，也可以调用 `curate`、`query` 和 `search` 等记忆工具。这样，记忆不再是一个黑盒 API，而是智能体推理循环中的一环。

整体架构包括三层：

1. **Agent Layer**：LLM 进行任务推理，同时决定需要保存什么知识；
2. **Execution Layer**：任务队列执行查询和整理操作，并通过沙箱限制 LLM 生成代码的访问范围；
3. **Knowledge Layer**：使用本地文件系统、层级 Context Tree、MiniSearch 全文索引和查询缓存保存知识。

##### Context Tree：层级化的文件知识图谱
ByteRover 用一个层级结构组织知识：

text

```plain
Domain > Topic > Subtopic > Entry
```

每个 Entry 是一个独立的 Markdown 文件，包含：

+ **Relations**：与其他知识条目的显式关系；
+ **Raw Concept**：原始来源、任务、修改内容、时间和作者；
+ **Narrative**：经过理解和整理后的规则、依赖、例子或解释；
+ **Snippets**：代码、公式或原始数据片段；
+ **Lifecycle Metadata**：重要性、成熟度、访问次数、更新时间等。Entry Structure

与向量检索中“两个文本相似，所以可能相关”不同，Context Tree 中的关系由创建该条知识的 LLM 明确声明。例如，一个条目可以显式引用另一个条目，并说明它们之间存在依赖、因果或补充关系。系统同时维护正向链接和反向链接，因此既可以从当前知识找到相关对象，也可以反向找到引用当前知识的条目。（建立显示的图链接状态，无非是具象的与抽象的）

### Adaptive Knowledge Lifecycle：让记忆可以演化
:::info
我感觉这个想法挺好的，因为记忆就是远的会被遗忘；重要性分数可以避免关键的记忆被遗忘，相当于一个自动演化的遗忘系统，不需要再额外设置过滤机制；但是问题在于，依旧每一次都要接受所有的记忆信息，无非是多了重要性与遗忘程度

:::

ByteRover 不把所有记忆看成永久且同等重要的事实，而是为每条知识设置生命周期。

它包含三个关键机制：

+ **重要性分数**：访问一次增加 3 分，更新一次增加 5 分，并以每日 0.995 的比例衰减；
+ **成熟度等级**：`draft → validated → core`；
+ **时间衰减**：越久没有更新，近期相关性越低，衰减常数设为 30 天，大约对应 21 天的半衰期。Knowledge Lifecycle

最终的检索得分不是单纯的 BM25 文本匹配，而是将三类信息结合起来：

$$   
\mathrm{Score}(n_i,q) = w_r \cdot \mathrm{BM25}(n_i,q) + w_\iota \cdot \hat{\iota}_i + w_t \cdot r_i  
$$

其中，第一项表示文本相关性，第二项表示知识重要性，第三项表示时间新鲜度。这样可以避免只因为某个旧条目与查询有词面重合，就把它排在更重要或更新的知识之前。

##### LLM 主导的记忆操作
ByteRover 支持五种基本记忆操作：

+ `ADD`：创建新条目；
+ `UPDATE`：替换现有条目；
+ `UPSERT`：存在则更新，不存在则创建；
+ `MERGE`：合并两个条目并删除源条目；
+ `DELETE`：删除一个条目或整个子树。Curation Operations

每个操作都包含 `reason`，因此系统不仅保存“改了什么”，还保存“为什么这样改”。在执行后，智能体会收到每个操作的成功或失败状态。例如，如果合并操作失败，智能体可以选择重试、修正路径，或者记录该问题供以后处理。这形成了一个**状态反馈闭环**

##### **五层渐进式检索（curation）**
策展机制，进行分层过滤，类似于筛选

**ByteRover 不会对每个查询都调用 LLM，而是采用五层检索策略：**

| **层级** | **机制** | **大致延迟** | **作用** |
| --- | --- | ---: | --- |
| **Tier 0** | **精确缓存命中** | **约 0 ms** | **查询和知识指纹都没有变化时直接返回** |
| **Tier 1** | **模糊缓存命中** | **约 50 ms** | **通过 Jaccard 相似度复用近似查询** |
| **Tier 2** | **MiniSearch/BM25** | **约 100–200 ms** | **对高置信度结果直接返回** |
| **Tier 3** | **单次优化 LLM 调用** | **小于 5 秒** | **将预取内容交给 LLM 综合回答** |
| **Tier 4** | **完整智能体循环** | **约 8–15 秒** | **对新颖、复杂或低置信度问题进行多轮推理** |


**这个设计的关键不是单纯追求低延迟，而是把不同查询交给不同强度的处理方式**

+ 熟悉的问题用缓存或关键词检索；
+ 有一定相关知识但需要综合的问题使用一次 LLM 调用；
+ 完全新颖或复杂的问题才启动完整 Agentic Loop。

系统还包含**域外检测（Out-of-Domain Detection）**：如果查询中的重要词在知识库中几乎找不到，且相关性分数低于阈值，系统会明确告诉智能体该问题可能超出当前记忆范围，而不是从不相关条目中强行生成答案。 （有急停，人为介入机制）

##### 具体实现
LLM 可以通过 ToolsSDK 使用：

+ `readFile()`：读取原始文件或已有知识；
+ `searchKnowledge()`：搜索 Context Tree 中已有的相关内容；
+ `curate()`：提交新增、更新、合并或删除操作；
+ 其他受控文件操作：辅助理解和整理资料。

而 Curation 至少要回答五个问题：

1. **这条信息是否值得记住？**
2. **它属于哪个领域、主题和子主题？**
3. **它是新知识，还是已有知识的补充或修正？**
4. **它与哪些已有条目存在关系？**
5. **应该新增、更新、合并还是删除？**

因此，Curation 更像：

过滤 + 语义理解 + 分类 + 去重 + 知识合并 + 来源追踪 + 生命周期管理。

### MemBrain
#### 解决的问题
核心问题是：**如何让长期运行的智能体拥有既保留自然语言语义，又具备明确结构、可更新、可追踪和高效检索的外部记忆。**

##### 文本中心的记忆系统
这类系统把记忆保存为文档、文本片段或日志，例如文件式记忆和一些 RAG 系统。

优点是：

+ 信息以自然语言保存，语义完整；
+ 模型可以直接读取；
+ 不需要把复杂事件拆成很多结构化字段。

但问题是：

+ 相关事实可能散落在不同文档中；
+ 事实之间没有显式关系；
+ 不容易追踪某个实体的变化；
+ 检索时可能找到相关文本，却无法组织出清晰的上下文。

##### 结构中心的记忆系统
另一类方法将记忆表示成实体和关系，例如：

```plain
(Alice, loves, MemBrain)
```

它们擅长：

+ 表示实体之间的关系；
+ 做实体消歧；
+ 沿着关系追踪依赖；
+ 进行较明确的结构化推理。

但问题是，三元组等表示方式容易把一个完整事件拆碎。原本一句自然语言就能表达清楚的信息，可能被拆成多条边，导致：

+ 上下文丢失；
+ 信息重构成本变高；
+ 关系模式需要预先定义；
+ 对复杂事件和时间信息的表达不够自然。

因此，MemBrain 想解决的是一个折中问题：

:::info
**如何同时保留文本的语义丰富性和结构化记忆的组织能力，而不是在二者之间二选一。**

:::

#### 如何解决问题
MemBrain 1.5 的核心设计是：**让数据库或预定义结构负责重复性的组织工作，让智能体负责需要语义判断的部分。**

它没有把记忆完全保存成文档，也没有把记忆完全拆成图中的节点和边，而是采用：

**自然语言事实 + 实体映射 + 面向实体的自适应语义树**

整体结构可以概括为：

```plain
实体 Entity
  └── 主题/方面 Aspect
        └── 自然语言事实 Fact
```

例如：

```plain
Caroline
  ├── Career
  │     ├── [Caroline] started a new job at [Feeling-AI]
  │     └── [Caroline] previously worked at [OpenAI]
  └── Travel
        └── [Caroline] traveled to Shanghai [last week::2026-03-10 to 2026-03-16]
```

其中：

+ **实体**表示人、组织、地点等对象；
+ **方面或主题**表示该实体下的某一类信息，例如职业、旅行；
+ **事实**仍然用自然语言保存，而不是拆成三元组。

##### 用自然语言事实避免信息碎片化
MemBrain 的事实不是简单的三元组，而是一个相对完整、自包含的自然语言语义单元。

这样做可以：

+ 保留原始事件的语义；
+ 让模型更容易直接理解；
+ 降低信息重构成本；
+ 方便加入时间、状态、事件细节。

事实中的实体用方括号显式标记，时间也会规范化，让事实同时具备自然语言可读性和结构化可索引性。

##### 用多对多实体—事实映射替代简单图边
MemBrain 不要求一个事实只对应两个实体。（多边图）

一个事实可以引用多个实体，一个实体也可以出现在很多事实中：

```plain
Fact 1 ── Caroline
       └─ Feeling-AI

Fact 2 ── Caroline
       └─ Shanghai
```

这比传统三元组更适合表达复杂事件。

##### 用实体版本历史追踪信息变化
实体的描述不是静态字段，而是可以随时间演化。

MemBrain 不会简单覆盖旧描述，而是保留版本历史。因此它可以记录：

+ 实体过去是什么状态；
+ 实体现在是什么状态；
+ 描述何时发生变化；
+ 新旧信息之间的关系。

这对回答“她现在在哪里工作？”和“她之前做什么？”这类时间敏感问题很重要。

##### 用实体层级树组织事实
对每个实体，MemBrain 都维护一棵层级树：

```plain
实体
 └── 方面/主题
      └── 事实
```

这棵树的结构约束是预先定义的，但具体内容由智能体动态决定：

+ 哪些事实属于同一主题；
+ 主题应该叫什么；
+ 新事实放到哪个分支；
+ 哪些主题需要拆分；
+ 哪些稀疏主题可以合并；
+ 中间节点应该如何总结。

因此，它结合了两种能力：

+ 预定义结构提供稳定性和效率；
+ 智能体提供灵活的语义组织能力。

#### 记忆写入流程
1. 对话分批处理

一个会话可能很长，因此系统先把会话拆成多个 batch，按顺序处理，并携带少量上下文，避免批次之间失去连续性。

整个会话处理完后，还会生成一个会话级摘要

2. 提取实体（类似于我现在的持续学习架构）

实体提取分成两轮：

1. 第一轮不带上下文，获取初始实体名称；
2. 系统检索已有的相关实体，再把这些实体作为上下文提供给第二轮智能体。

这样可以处理实体消歧

3. 提取事实

在实体列表确定后，智能体提取事实，并要求事实显式引用实体，同时规范化时间表达

4. 实体解析与更新

对于新提取的实体，系统判断它是：

+ 一个全新的实体；
+ 已有实体的新别名；
+ 与已有实体相同但名字不同；
+ 一个容易混淆的不同实体。

简单情况可以通过名称匹配处理，复杂情况交给智能体判断。

5. 更新实体层级树

新事实先挂到实体下面，随着事实数量增加，系统再把相关事实聚类成主题

如果某个主题变得过于拥挤，就拆分；如果某些主题过于稀疏，就合并。高层节点还会生成摘要，使树保持紧凑。

#### 检索记忆
+ 关键词检索
+ 向量检索
+ 结构感知检索

系统先定位相关实体，再沿着实体树定位相关主题，最后寻找事实。

+ 合并、去重和重排序

三路检索结果会被：

    1. 合并；
    2. 去重；
    3. 重新排序；
    4. 保留不同主题下具有代表性的事实。

最终上下文会按实体和主题组织

+ 对复杂问题进行反思式检索

对于简单问题，一轮检索可能就够了。

系统可以让一个反思智能体检查当前检索结果是否足够。如果信息不完整，它会生成后续查询

从“一次性查询”变成“先检索—判断缺口—补充检索”

### A-Mem
核心思想：**让记忆系统本身也具备一定的 agentic behavior，由 LLM 主动决定记忆如何描述、如何连接以及如何演化。**

#### 解决的问题
当智能体与环境进行长期、多轮交互时，如何自动地组织、连接、更新和检索过去的经验，使其能够利用跨时间、跨对话的信息完成复杂任务？

普通的 LLM agent 虽然能够调用工具、执行任务和进行推理，但如果没有外部记忆，它很难保留长期交互中的关键信息。传统记忆系统通常能够“存储”和“检索”历史内容，却不擅长理解不同记忆之间的关系，也不能随着新经验的加入而自动重组知识结构。论文认为，这会限制智能体在开放环境和长时间交互中的泛化能力。

#### 前人工作
+ 直接保存完整交互记录
+ 使用固定的记忆结构或记忆控制器
+ 图数据库或图结构记忆

过去的方法大多解决了“怎么保存”和“怎么找回”的问题，但没有充分解决：

1. 新记忆应该如何自动组织？
2. 不同记忆之间应该建立什么联系？
3. 新经验加入后，旧记忆是否应该被重新解释或更新？
4. 如何在没有人工预定义 schema 的情况下形成动态知识网络？

#### 如何解决问题
##### 记忆笔记构建：把原始交互转化为结构化 note
当智能体产生一条新记忆时，A-MEM 不只是保存原始文本，而是为它生成一份结构化的“记忆笔记”。

每个记忆包含：

+ 原始交互内容；
+ 时间戳；
+ 关键词；
+ 标签；
+ 上下文描述；
+ 向量表示；
+ 与其他记忆的链接集合。

其中比较重要的是 **context**。它不是对原始内容的简单摘要，而是由 LLM 生成的一句话语义描述，用来解释这条记忆的主题、主要观点和用途。

##### 链接生成：让新记忆主动寻找相关记忆
当加入一条新记忆时，A-MEM 首先使用 embedding 检索最相似的历史记忆，而不是与所有历史记忆进行昂贵的比较。

相似度使用余弦相似度：

$$   
s_{n,j} = \frac{e_n \cdot e_j}{\lVert e_n\rVert \lVert e_j\rVert}  
$$

系统选出 top-$k$ 个候选邻居，然后交给 LLM 判断这些记忆之间是否存在有意义的关系。关系不只是“文字相似”，还可以包括：

+ 主题相同；
+ 共享某些概念；
+ 一个记忆补充另一个记忆；
+ 存在因果或时间关系；
+ 多条记忆共同构成一个更高层次模式。

因此，embedding 主要负责高效筛选候选对象，LLM 负责进行更细粒度的语义判断。

##### 记忆演化：新经验可以修改旧记忆
A-MEM 最有特色的部分是 **Memory Evolution**。

传统系统通常将旧记忆视为固定内容：写入之后，最多调整权重或删除它。但 A-MEM 允许新记忆反过来影响旧记忆。

对于新记忆的近邻记忆，LLM 可以重新判断：

+ 旧记忆的上下文描述是否需要更新；
+ 关键词是否需要补充；
+ 标签是否需要调整；
+ 是否需要建立新的连接；
+ 多条记忆是否应该形成更高层次的组织。

因此，随着更多交互加入，记忆库不是简单地不断增长，而是会逐渐重新组织和丰富。作者认为，这类似于人类学习过程：后来获得的经验可能会改变我们对早期经验的理解。

##### 相对记忆检索：检索相关记忆及其关系
对于当前查询，A-MEM 首先把查询转换成向量，再从记忆库中检索 top-$k$ 条相关记忆。

如果一条被检索到的记忆与其他记忆存在链接，那么系统还可以进一步访问这些相关记忆。这使得系统不只返回孤立的相似文本，也可以返回一个由多个相关记忆组成的局部知识结构。

因此，A-MEM 的记忆使用过程可以概括为：

先通过向量相似度找到入口记忆，再通过记忆之间的连接扩展上下文。

#### benchmark
+ LoCoMo

LoCoMo 用来评估长期对话中的问答和记忆能力。它具有以下特点：

    - 对话平均约 $9{,}000$ 个 token；
    - 最多跨越 35 个 session；
    - 总共包含 7,512 个问答对；
    - 任务包括五类： 
        1. Multi-Hop：需要跨多个 session 综合信息；
        2. Temporal：需要理解时间关系；
        3. Open-Domain：需要结合对话和外部知识；
        4. Single-Hop：单个 session 就能回答；
        5. Adversarial：需要判断问题是否无法回答。

因此，LoCoMo 特别适合测试“能否跨很长时间保持记忆和一致性”。

+ DialSim

DialSim 用来测试长期、多方对话中的记忆能力。其数据来源包括：

    - 《Friends》；
    - 《The Big Bang Theory》；
    - 《The Office》。

数据包含约 1,300 个 session，覆盖五年时间，总规模约 350,000 个 token，并包含大量基于对话和时间知识图谱构造的问题。

#### 性能评估
1. F1

F1 用来衡量答案与参考答案在词语层面的匹配程度，综合考虑：

    - Precision：生成答案中的内容有多少是正确的；
    - Recall：参考答案中的信息有多少被覆盖。
2. BLEU-1

BLEU-1 主要衡量生成答案与参考答案之间的 unigram 重叠，反映词汇层面的匹配程度。

+ ROUGE-L 和 ROUGE-2
    - ROUGE-L：基于最长公共子序列；
    - ROUGE-2：基于二元词组重叠。

它们用于评估答案与参考答案之间的文本重合和局部顺序。

+ METEOR

METEOR 不仅考虑精确词匹配，还会考虑词形、同义词和一定程度的语义对应，因此比纯粹的词面匹配更宽松。

+ SBERT Similarity

SBERT Similarity 使用句向量计算生成答案与参考答案之间的余弦相似度，用于衡量语义相似性。论文还报告了回答所需的平均 token 数，以评估系统的计算和上下文成本。

## 思考
当前 Agent Memory 研究试图解决的问题比普通向量数据库更复杂：

1. 如何识别哪些信息值得长期保存；
2. 如何区分用户事实、Agent 经验和主观判断；
3. 如何处理同一事实随时间变化；
4. 如何处理相互矛盾的信息；
5. 如何根据实体、时间和因果关系检索；
6. 如何控制记忆的新鲜度；
7. 如何让 Agent 在不同会话中保持一致；
8. 如何让 Agent 的观点能随着证据改变；
9. 如何在记忆错误时追溯来源；
10. 如何删除、修改或撤销记忆。

## 三、核心趋势与思考
### 3.1 技术演进路线
```plain
直接存完整上下文 → RAG检索片段 → 事实抽取+更新 → 结构化记忆组织 → 闭环反馈修复
  (MemGPT)          (传统RAG)       (Mem0)         (GAM/MemBrain)    (MemMA/Hindsight)
```

### 3.2 六个关键设计维度的矛盾与解法
| 维度 | 核心矛盾 | 代表性解法 |
| --- | --- | --- |
| **粒度** | 精确事实 vs 完整上下文 | 三元组+摘要互补(Memori); 双粒度保存(GAM); MemCell多组分(EverMemOS) |
| **结构** | 灵活自然语言 vs 刚性图结构 | 自然语言事实+实体映射(MemBrain); LLM主导策展(ByteRover) |
| **更新** | 实时更新延迟 vs 离线整合质量 | 在线soft+离线sleep(LightMem); probe QA验证(MemMA) |
| **检索** | 召回率 vs 噪声控制 | 自适应悬崖剪枝(VCRM); 判断-改写-再检索循环(MemMA/EverMemOS) |
| **模态** | 文本记忆 vs 视觉记忆 | 统一跨模态编码空间(TMM); 文本渲染为图像压缩(VCRM) |
| **遗忘** | 保留信息 vs 控制成本 | 知识生命周期衰减(ByteRover); 观点置信度演化(Hindsight) |


### 3.3 七条共性发现
1. **LLM-as-a-Judge 已成为标准评估方式**，F1/BLEU 降为辅助指标
2. **LoCoMo 和 LongMemEval 是事实标准 benchmark**，覆盖大多数记忆能力维度
3. **"判断-改写-再检索"闭环检索**逐渐取代单次 top-k，成为检索质量提升的关键
4. **记忆不只是存储问题**，而是编码→检索→利用→修复的完整生命周期
5. **事实与信念分离**(Hindsight)和**记忆主动演化**(ByteRover)是较前沿方向
6. **效率导向**(LightMem预压缩、ByteRover五层检索)与质量导向存在持续张力
7. **当前置信度判断普遍粗糙**：多依赖LLM主观判断，缺乏不确定性量化和证据可靠性加权
