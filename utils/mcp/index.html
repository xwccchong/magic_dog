    MCP 外部工具集成 (mcp_servers)¶

    文件路径：src/mcp_servers/

    基于 Model Context Protocol 的客户端实现，为 LLM 大脑提供动态外部工具扩展能力。

    本模块让 MAGIC 的 LLM 能够发现并调用外部 MCP 服务器暴露的任意工具——相当于给 LLM 装上"插件系统"，无需修改代码即可扩展机器人的能力边界。

    MCP 是什么¶

    MCP（Model Context Protocol） 是 Anthropic 提出的开放协议，标准化了 LLM 与外部工具/服务的交互方式：

    协议 角色 类比
    HTTP 浏览器 ↔ 服务器 获取网页
    MCP LLM ↔ 外部工具 获取能力

    一个 MCP 服务器可以暴露任意工具（查数据库、调 API、读文件、发邮件...），LLM 通过 MCP 客户端发现工具的 schema 后，自主决定何时调用、传什么参数。

    文件结构¶

    src/mcp_servers/
├── __init__.py              # load_mcp() 工厂函数
├── client.py                # ★ MCPClientManager：连接管理 + 工具发现 + 调用
└── orchestrator.py          # ★ MCPOrchestrator：运行时调度（分流/去重/回填结果）

    MCPClientManager — 连接管理¶

    定义位置：src/mcp_servers/client.py

    三种传输方式¶

    class TransportType(str, Enum):
    STDIO = "stdio"   # 启动子进程，通过 stdin/stdout 通信
    SSE = "sse"       # HTTP Server-Sent Events 长连接
    HTTP = "http"     # Streamable HTTP 流式请求
    传输方式 适用场景 特点
    STDIO 本地工具（同机器上的独立进程） 延迟最低，无网络开销
    SSE 远程 HTTP 服务 单向推送，兼容性好
    HTTP 远程 Streamable HTTP 双向流式，需服务端支持

    配置文件声明¶

    在 JSON5 配置中添加 mcp_servers 列表：

    mcp_servers: [
  {
    name: "my_tool_server",
    transport: "stdio",
    command: "python",
    args: ["-m", "my_mcp_server"],
    env: { "API_KEY": "xxx" }
  },
  {
    name: "web_api",
    transport: "http",
    url: "http://localhost:8000/mcp",
    headers: { "Authorization": "Bearer xxx" }
  }
]

    核心流程¶

    MCPClientManager.start()
  │
  ├── 为每个 server 创建独立 asyncio Task
  │     │
  │     ├── ① 建立连接 (_connect_server)
  │     │      stdio: 启动 command + args 作为子进程
  │     │      sse:   sse_client(url)
  │     │      http:  httpx.AsyncClient → streamable_http_client(url)
  │     │
  │     ├── ② 初始化 MCP 会话
  │     │      session = ClientSession(read, write)
  │     │      await session.initialize()
  │     │
  │     ├── ③ 发现工具
  │     │      tools = await session.list_tools()
  │     │      → 每个 tool 注册为 MCPTool 对象
  │     │      → 命名规则: mcp_{server_name}_{tool_name}
  │     │
  │     └── ④ 等待关闭信号
  │            await close_event.wait()
  │
  └── 所有 server 就绪后
        get_tool_schemas() 返回 OpenAI function 格式
        → 注入到 LLM.function_schemas

    Tool Schema 转换¶

    MCP 返回的工具描述被转换为 OpenAI function-calling 格式，LLM 才能理解：

    @dataclass
class MCPTool:
    key: str            # "mcp_my_server_search_docs"
    server_name: str
    original_name: str  # "search_docs"
    description: str
    input_schema: dict

    def convert_to_schema(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.key,          # mcp_ 前缀避免与内置工具重名
                "description": self.description,
                "parameters": self.input_schema,
            },
        }

    MCPOrchestrator — 运行时调度¶

    定义位置：src/mcp_servers/orchestrator.py

    嵌入在 LLM Cortex 的 tick 循环中，负责运行时编排。

    关键参数¶

    参数 默认值 说明
    max_concurrency 5 最多 5 个 MCP 工具并发调用
    max_rounds 5 最多 5 轮 tool-calling 回路（防止死循环）

    核心方法¶

    class MCPOrchestrator:
    async def start(self):
        """连接所有 MCP server + 将 tool schemas 注入 LLM"""

    async def execute_mcp_actions(self, actions, succeeded_calls) -> tuple:
        """从 LLM 输出中筛选 MCP 动作，去重后并发执行"""

    def extract_om1_actions(self, actions) -> list:
        """分离 MCP 工具调用和 OM1 原生动作（speak/move/grasp...）"""

    def build_result_prompt(self, prompt, results) -> str:
        """将工具返回结果拼回 prompt，供 LLM 下一轮参考"""

    去重机制¶

    同一工具 + 同一参数 = 只执行一次：

    def build_call_signature(self, action) -> str:
    args = self._parse_arguments(action)
    return f"{action.type}|{json.dumps(args, sort_keys=True)}"
    # 例: "mcp_weather_get_forecast|{"city":"北京"}"

    同时在 build_result_prompt 中明确告知 LLM：

    [Next Step]
Do NOT re-call tools you have already called successfully.
If all needed info is available, respond with your final actions.
Otherwise call only the necessary tools in one batch.

    完整执行流程¶

    以"查天气并播报"为例：

    Tick 开始: LLM 收到 prompt + 所有 MCP tool schemas
    │
    ▼
LLM 输出: [
  {type: "speak", value: "让我查一下天气"},      ← OM1 动作（直接执行）
  {type: "mcp_weather_get_forecast", value: {city: "北京"}},  ← MCP 工具
]
    │
    ▼
MCPOrchestrator.execute_mcp_actions()
    ├── extract_om1_actions() → [speak] → 直接发给执行器
    └── is_mcp_tool("mcp_weather_get_forecast") → True
        │
        ├── 检查 signature 是否已调用过
        │   "mcp_weather_get_forecast|{"city":"北京"}" → 未调用
        │
        ├── 并发执行 (asyncio.Semaphore 限制最多 5 个)
        │     session.call_tool("get_forecast", {city: "北京"})
        │     → 返回: "北京今天晴，25°C"
        │
        └── 标记 signature 为 succeeded

    ▼
build_result_prompt():
    "[mcp_weather_get_forecast] OK: 北京今天晴，25°C"
    "不要重复调用已成功的工具。如果信息足够，输出最终动作。"

    ▼
下一轮 LLM: "北京今天晴，25°C"
    → 输出: {type: "speak", value: "北京今天晴，气温25摄氏度"}

    为什么需要 MCP¶

    传统方式 MCP 方式
    每个外部 API 需要手写 Python 连接器 任何人提供 MCP server 即可即插即用
    新工具 = 改代码 + 重新部署 新工具 = 加一行 JSON5 配置
    工具能力对 LLM 是硬编码的 LLM 自动发现工具 schema，自主决策调用
    只支持 Python 生态 任何语言都能实现 MCP server

    本质上，MCP 让 MAGIC 从"我有哪些写死的动作"变成"我能动态发现并调用外部世界的任意能力"——LLM 不再受限于代码中预定义的工具列表，而是可以连接到不断增长的 MCP 生态中。

    配置文件示例¶

    完整 JSON5 配置¶

    {
  mcp_servers: [
    // ① 本地 STDIO server — 启动一个 Python 子进程
    {
      name: "knowledge_base",
      transport: "stdio",
      command: "python",
      args: ["-m", "kb_mcp_server"],
      env: {
        "KB_DB_PATH": "/data/knowledge.db"
      }
    },
    // ② 远程 HTTP server
    {
      name: "weather",
      transport: "http",
      url: "http://10.0.0.100:8080/mcp",
      headers: {
        "Authorization": "Bearer ${WEATHER_API_KEY:-}"
      }
    },
    // ③ 远程 SSE server
    {
      name: "calendar",
      transport: "sse",
      url: "http://10.0.0.101:3000/sse"
    }
  ]
}

    环境变量¶

    # 设置 API Key（配置文件中用 ${WEATHER_API_KEY:-} 引用）
export WEATHER_API_KEY=sk-xxxxx

    架构设计要点¶

    1. 独立 Task 管理：每个 MCP server 跑在独立 asyncio Task 中，一个 server 挂掉不影响其他
    2. 优雅降级：连接失败时只打日志，不阻塞主循环
    3. 去重保护：同一调用不重复执行，防止 LLM 循环
    4. 超时保护：单次 MCP 调用 10 秒超时，防止阻塞整个 tick
    5. 轮次限制：最多 5 轮 tool-calling，防止无限回环
    6. schema 隔离：MCP 工具统一加 mcp_ 前缀，避免与系统内置动作重名
